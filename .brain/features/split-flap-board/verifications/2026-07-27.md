## Golden path

A TV owner signs in, opens the board on the TV, and a write pushed over the board socket ripples across the flaps.

The write was pushed by opening a second `WebSocket` **from inside the page** (`page.evaluate`), so the browser's own session cookie authenticated the upgrade. The room's current revision was read from that socket's first `state` event (`revision: 6` on connect).

Step 02 first writes a neutral `BOARD IDLE` baseline (revision 6 → 7) so the run is repeatable: the room is last-write-wins and only *changed* cells flip, so re-running against a board that already read `HELLO TV` would legitimately animate nothing. The measured write is revision 7 → 8.

Sampled in-page with `requestAnimationFrame`, counting faces whose computed `opacity` is strictly between 0 and 1 (the flap animates `transform` and `opacity` on one transition, so a fractional opacity *is* a tile in flight). `t=0` is the instant the `set` frame was written to the socket; 84 frames sampled over 1400ms.

| Metric | Measured |
|---|---|
| First tile starts moving | **117ms** |
| Peak concurrency | **42 faces (21 tiles) at 267ms** |
| Last tile still moving | **417ms** (next sample, 449ms, is 0) |
| Total motion window | **~117 → ~450ms** |

Face-count series (`t:faces`): `18:0 49:0 82:0 117:4 149:12 183:20 216:32 250:40 283:42 316:34 350:22 383:14 417:6 449:0` … 0 for the remainder.

This matches the declared constants (`FLAP_STAGGER_MS = 14`, `FLAP_DURATION_MS = 220`) rather than merely "looking animated". The changed cells begin at column 6–7, so the earliest stagger delay is `(0+7)×14 = 98ms` (observed first motion 117ms, i.e. 98ms + socket round-trip + one rAF of sampling granularity), and the latest changed cell is row 1 col 16 → `(1+16)×14 = 238ms` delay, ending at `238 + 220 = 458ms` (observed last motion 417ms, settled by 449ms). The single-humped curve rising to 42 concurrent faces and back to zero is the ripple, not a simultaneous swap.

Worth recording for future runs: the widest mid-flight window for this message is **~+230ms**, not ~150ms, because the stagger clock starts at column 6–7 rather than column 0. Screenshotting at +150ms catches only ~4–12 faces; +215ms catches 32.

### Discarded first run — dev-server artifact, not an app defect

The very first attempt failed before step 01 completed, with 504s on `/node_modules/.vite/deps/{react,superjson,react-hook-form,@tabler_icons-react}.js`. Cause: the dev server had just logged `Re-optimizing dependencies because lockfile has changed` and was mid-optimize, so Vite served 504 "Outdated Optimize Dep" for those modules; the page never hydrated. Confirmed by the server log line `✨ new dependencies optimized: …` followed by `optimized dependencies changed. reloading`. Warming the optimizer and re-running produced the clean run recorded above. Not counted against the verdict — but it did surface finding #2 below.

## Findings for main thread

1. **Every `data-testid` this walk needed already exists** — `flap-tile` (with `data-char` / `data-color`), `board-display` (with `data-status`), `board-grid`, `board-qr-overlay`, `board-qr-image`, `board-sound-unlock`, `board-status-chip`. Nothing was added and nothing was missing.
2. **Security-adjacent, belongs to the auth feature, not this one:** the login form has no `method`/`action`, so when client JS fails to load (the Vite 504 case above) the browser falls back to a **native GET submit** and the credentials land in the URL — the discarded run navigated to `/login?email=admin%40preview.local&password=Password123%21`. That puts a password in browser history, and in the `Referer` of any subsequent request. Narrow trigger (requires JS to be dead), cheap fix (`method="post"`, or a submit handler that hard-blocks non-JS submission). **Reported, not fixed** — outside this feature and outside a verifier's remit.
3. **The unknown-board 404 is the unstyled React Router default boundary** — a bare full-white page with unstyled black text and an empty `document.title`. Functionally correct (404, no crash, no stack, non-enumerable), so E1 passes. But `/b/:boardId` is a kiosk surface: a wall-mounted TV that reloads onto a bad id flashes a full-screen white page in a dark room. Consider a themed, dark 404 boundary for the board route. Not a blocker.
4. **A coloured space is a lit tile — visible in `04-settled.png`.** `{ text: "HELLO TV", color: "yellow" }` yields **8** yellow tiles, including the separator space, which renders as a lit yellow blank between `HELLO` and `TV`. This is exactly the documented Phase 1 rule ("a space with no colour of its own is a separator; a space with a colour is a tile"), so it is correct, not a bug. Flagging it only because a writer wanting an unlit gap must split the segment rather than rely on the space — worth a line in the phone-controller UX when phase 4 lands.
5. **The display exposes no revision in the DOM.** `data-status` carries socket status only, so a verifier (or a debugging human) has to open a socket to learn the room's revision. A `data-revision` attribute on `[data-testid="board-display"]` would make revision assertions and manual TV debugging trivial. Nice-to-have, not required.
6. **Re-running the same write is a no-op animation, by design.** My first pass asserted mid-flip after writing `HELLO TV` to a board that already read `HELLO TV` from the previous run — 0 tiles flipped, which is *correct* (only changed cells animate, per `changedCellCount`) but made the assertion order-dependent. The script was made self-resetting (write `BOARD IDLE`, settle, then the measured write). Any future automation of this feature needs the same care.

## Verdict rationale

**✅ PASS.** Every asserted state was reached in a real headless browser against the live dev server and screenshotted. The 144-tile invariant held exactly (`flap-tile` count = 144, CSS grid 24×6), the display reported `data-status="live"`, and the board laid out full-bleed at 1280×640 in a 1280×720 viewport with no scrollbars on a pure-black field. A `set` command pushed over the page's own authenticated WebSocket advanced the room 7 → 8 and produced a genuine staggered ripple — 42 concurrent faces mid-`rotateX` at peak, motion spanning ~117–450ms, quantitatively consistent with the declared 14ms/tile stagger and 220ms flip rather than a simultaneous swap — settling to the exact text sent (`HELLO TV` / `FLAPPYBOARD`) with the exact colours sent (8 yellow, 11 green) read straight off `data-char`/`data-color`. The QR overlay was proven to encode the real controller URL by pixel-identical comparison against a freshly generated code (0/262,144 pixels differing, versus 28.6% for a control), not merely by checking that `src` was non-empty. The sound-unlock prompt was present before any gesture and detached after a real click. The one error path returned a true 404 with no crash, no leaked stack, and no 403. `jsErrors` was empty and the only `networkError` was the intentional `404@E1`. The four findings above are observations and one out-of-scope auth hardening suggestion; none of them is a defect in this feature's golden path.
