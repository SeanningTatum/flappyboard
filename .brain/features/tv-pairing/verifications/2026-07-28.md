## The claim, and how it was proven

A TV must reach a board **without ever holding the owner's login**. Proving that
needs two isolated browser contexts, not one page: **context 1 is the TV and was
asserted to hold zero cookies before anything happened** (`context.cookies()` →
`[]`), context 2 is the owner's signed-in phone. The same discipline the
`phone-control` verification used, run in the opposite direction.

## Error paths

| # | Step | Observed | Result |
|---|------|----------|--------|
| E1 | Bogus code `ZZZZZZ` at `/link` | *"No TV is waiting on that code. Check it, or reload the TV for a new one."* | ✅ |
| E2 | **Replay** — the same code submitted a second time | Refused with the identical message; `link-success` never shown. Single-use holds | ✅ |
| E3 | **Cookie-evicted TV** — device cookie cleared, board URL reloaded | Redirected to `/tv` with a fresh code (`BT27G8`), **not a 404** | ✅ |
| E4 | **Stranger** — no cookies at all, direct `GET /b/<boardId>` | **HTTP 302 → `/tv`**, confirmed with `curl`. Never sees board content | ✅ |

E3 is the mitigation decision 2 exists for: the Samsung built-in browser evicts
cookies aggressively, so a TV that lost its grant must offer re-pairing rather than
a dead end. E4 confirms the redirect is not a hole — a stranger gets the pairing
screen, not the board.

## A worker observation that did not survive checking

Run B reported the device cookie carrying a **"~15-day expiry"**, which would
contradict the 180-day device grant the feature doc specifies — and would matter,
because decision 2 makes cookie lifetime the load-bearing risk for a wall-mounted
TV. Checked rather than accepted:

```
DEVICE ttl secs: 15552000 = 180 days
GRANT  ttl secs:  2592000 =  30 days
Set-Cookie: fb_device_abc-123=fbd1.x.y; Path=/; HttpOnly; SameSite=Lax; Max-Age=15552000
```

`claimHandoff` passes `DEFAULT_DEVICE_TTL_SECONDS` (`app/trpc/routes/board.ts:1230`),
and `Max-Age=15552000` is **exactly 180 days**. The report was a misreading of the
leading digits of `15552000`, not a defect. Recorded because the next person reading
run B's raw output would otherwise chase a bug that is not there.

## Findings for main thread

- **Not a pairing bug, but a real harness hazard, and it bit both runs:** clicking
  the login submit before React hydrates fires a native form submit and yields a
  bogus **405 Method Not Allowed**. `login-form.tsx:71-79` already documents this in
  a comment. Any future walk should use the `login-email` / `login-password` /
  `login-submit` testids and wait for hydration — `e2e/auth.spec.ts` is the
  reference.
- No missing `data-testid`s. `tv-pairing`, `tv-code`, `link-root`, `link-code`,
  `link-board`, `link-submit`, `link-success`, `link-error` were all found without
  guesswork.

## Not proven

- **The decisive test for decision 2, and it is owner-only:** power-cycle the real
  Samsung TV and confirm `fb_device_<boardId>` survives. E3 proves the app recovers
  *gracefully* when the cookie is gone; it does not prove the cookie *persists* on
  that specific browser. If it does not, decision 2 (the built-in browser over a
  kiosk stick) has to be revisited — the 180-day Max-Age is necessary but not
  sufficient.
- **Concurrent redemption of one code.** Single-use is proven sequentially (E2) and
  the atomicity is unit-tested under `blockConcurrencyWhile`, but no live N-way race
  was run here.
- **The approve-device spend cap** (`DEFAULT_QUOTA["approve-device"]`, 8/hour per
  owner and 16/hour per board — the deliberate substitute for the plan's per-code
  attempt cap). Unit-tested, not driven to its limit in a browser.

## Verdict rationale

PASS. The feature's central claim was measured, not reasoned about: a context
asserted to hold **zero** cookies ended up rendering a live 144-tile board while
holding **only** an `HttpOnly` device grant and no session cookie, and it got there
by socket push without a reload. Both refusal paths hold, a replayed code is
refused, a cookie-evicted TV is offered re-pairing instead of a 404, and a stranger
with no cookies is redirected rather than shown the board. Two independent runs
agreed throughout, on distinct codes. The one worker claim that conflicted with the
spec was checked and found to be a misreading rather than a bug.

Scoped honestly: this says the device-code flow works in a real browser. It does
not say the cookie survives a Samsung TV power cycle — which is the one thing only
the owner can test, and the one thing decision 2 rests on.
