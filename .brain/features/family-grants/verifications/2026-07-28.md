# Verification: Family Grants

- **Slug**: `family-grants` (feature memo: `.brain/features/family-grants/family-grants.md`)
- **Date**: 2026-07-28
- **Verified by**: coordinator delegating to three worker sub-agents (Sonnet) driving the Playwright CLI; bundled Chromium, clean per-actor contexts, `--disable-extensions`
- **Base URL**: http://localhost:5174 _(dev server started by agent)_
- **Boards**: run A `7462732b…`, run B `8958b250…`, run C `605171b1…` — one per run, so no run could contaminate another's grants
- **Verdict**: ✅ PASS on all three claims the feature doc requires. Two findings recorded, one of which is a **half-implemented decision** and needs an owner call before ship.

## What the feature doc says a walk must show

> a grant older than the old 12h ceiling still opens a socket; per-device revoke
> kills exactly one device and leaves the others live; `grantEpoch` bump still
> kills all.

All three are covered below. Every phone in every run was paired through the
**real QR flow** — scrape the single-use `?t=` token off the TV display as owner,
redeem it in a **fresh cookie-less context** — and every one ended holding exactly
one cookie, `fb_grant_<boardId>`, with **no session cookie** and
`control-root[data-access]="grant"`.

## Claim 1 — the 30-day TTL (was 12 hours)

Run B decoded the signed cookie payload rather than eyeballing it, and showed the
arithmetic **deliberately**, because an earlier worker on this branch misread
`15552000` as "~15 days" when it is 180:

```
issuedAt  1785288855520 ms
expiresAt 1787880855520 ms
diff      2 592 000 000 ms → 2 592 000 s → 2 592 000 / 86 400 = 30.0 days
```

Matches `DEFAULT_GRANT_TTL_SECONDS` (`pairing.ts:94`). Run B also explicitly noted
it did **not** conflate this with `DEFAULT_DEVICE_TTL_SECONDS` = 180 days, which is
the TV cookie and a different epoch entirely. ✅

## Claim 2 — per-device revoke isolation (the central one)

Run A, two phones on one board, one row un-paired:

| Phone | After the un-pair | Evidence |
|-------|-------------------|----------|
| **A** | **survived** | `"Sent to the board"`, 200 on `board.setMessage`; after reload still `data-access="grant"`, editor functional, history carried the new entry |
| **B** | **died** | **401** on `board.setMessage`; banner *"Your access expired. Scan the code on the board again."*; after reload the page is replaced by the expired-grant screen |

`report.json`: `phoneADied: false`, `phoneBDied: true`. Device rows went 2 → 1.
**Exactly one died, exactly one survived** — the sibling grant was untouched. ✅

Revoked phone's full-page copy: title **"SCAN THE BOARD AGAIN"**, body *"This link
has expired. Point your phone at the code on the board to take control again."*,
button **"TRY AGAIN"**.

## Claim 3 — `grantEpoch` bump kills every phone

⚠️ **This claim was nearly missed because the coordinator's first brief was wrong.**
Run B was pointed at `board-devices-unpair-displays` and told to treat it as
"revoke all". It is not — it bumps `deviceEpoch` and hits **televisions only**. Run
B correctly refused to report a failure, cited the component's own doc-comment
(`board-devices.tsx:28-30`), and observed both phones still working, which is the
*designed* behaviour. Run C was dispatched to test the right control.

There are three deliberately distinct controls:

| Control | Bumps | Kills |
|---------|-------|-------|
| `board-device-unpair` (per row) | a tombstone keyed by the grant nonce | one phone |
| `board-card-revoke` | `grantEpoch` | **every phone at once** |
| `board-devices-unpair-displays` | `deviceEpoch` | every TV, **no phone** |

Run C, three phones, one `board-card-revoke`: **all three refused, uniformly and
simultaneously** — 401 on `setMessage` ×3, each showing the rescan copy. No phone
survived. Re-pairing with a fresh token restored phone A to `data-access="grant"`
and a subsequent send returned 200, so the recovery path works. ✅

The confirmation copy on each is precise about which population it touches, and
that precision is what saved run B from a false report:

- **TV control** — *"Every television showing this board goes back to the pairing screen. **Paired phones are not affected.**"*
- **Phone control** — *"Every phone that scanned this board loses control immediately, and the code on your TV stops working until the display refreshes it a few seconds later."* (the QR going stale is a consequence of `grantEpoch` being inside the token's MAC, not a TV un-pair)

## Grandfathering

The doc's load-bearing rule is *"a grant with **no record** is LIVE, not dead"* —
revocation is an explicit tombstone, because reading absence as revocation would
have silently un-paired every phone in existence on deploy. Run B corroborated it:
a phone paired *after* the owner had already loaded the device list worked
immediately. Honest limit: true grandfathering concerns pre-deploy grants with zero
DB record and is **not reproducible through the live UI** — `decideTouch` in
`paired-devices.ts` is unit-tested on all four combinations, and that remains the
real proof.

## Findings

### 1. Device naming is never captured — decision 4 is half-implemented

Run A: the owner's list showed **two textually identical rows** —
`"Unnamed phone / Last used just now / Un-pair"` — and reported
`rowsDistinguishable: false`. **The owner cannot tell which phone is which.**

This is not cosmetic. `board.ts:155-160` states the field's whole purpose:

> *"The name this device was given at pairing, if it gave one. Owner-facing only —
> it exists so 'un-pair Kai's phone' is a thing the owner can say"*

And the TV plan's decision 4 chose "name at pairing, owner-visible" precisely
because *"un-pair Kai's phone beats bump the epoch and re-pair everyone"*.

The read path is wired — `device.name` is consumed at `board.ts:303` and threaded
through `BoardAccess`. **Nothing ever sets it.** `control.tsx:48` calls
`board.pair({ boardId, token })` with no name, and no caller anywhere supplies one;
`deviceName: null` is hard-coded at `:232` and `:1059`. There is also no rename
affordance in the owner's list (the row testids are `board-device`,
`board-device-unpair`, `board-device-unpair-confirm`, `board-device-unpair-error` —
no rename).

So per-device revoke is mechanically correct and its isolation is proven, but the
capability decision 4 exists to deliver is not reachable from the UI. **Owner call
needed: wire the name capture before shipping, or ship with this as a stated gap.**

### 2. `/boards` hard-crashed once on first hydration (dev only, not reproduced)

Run A hit `TypeError: Cannot read properties of null (reading 'useRef')` inside a
Radix `Dialog`, surfaced as "Oops!", on its very first visit to `/boards`. A reload
and every subsequent context loaded cleanly, and it never recurred. The worker read
it as a Vite dev-server dependency-optimisation race on first hydration, which fits
the evidence (first-request-only, self-healing on reload).

Recorded rather than dismissed, because it is a crash on a route users hit. It is
**not attributed to this feature** and was **not reproduced**; it deserves a look
during the `kiosk-display` soak or a production-build check, not a fix here on
speculation.

### 3. Harness trap worth keeping

Run C found `control-root[data-access]` still reading `"grant"` on all three phones
*after* the revoke — a stale client-side attribute, because the loader does not
re-run without navigation. The server refused the writes, which is what matters,
and run A confirmed the attribute flips to `"none"` after a reload. **A future walk
asserting only on `data-access` would record a false pass.** Assert on the write
outcome.

## Console

- **jsErrors** — none across all three runs except the *expected* 401 console lines
  on revoked sends (run A ×1, run C ×3), plus the unreproduced `/boards` crash in
  finding 2.
- **networkErrors** — only the expected refusals: `phoneB@401` (run A),
  `401@setMessage ×3` (run C). Every other `/api/trpc/*` call was 200.

## Verdict rationale

PASS on all three required claims, each measured rather than reasoned about, and
each on its own board so no run could contaminate another. The central claim —
revoke isolation — was proven by outcome, not by attribute: one phone kept writing
with a 200 while its sibling took a 401 from the same action.

Claim 3 is worth reading as a process note as much as a result. The coordinator's
first brief mislabelled the TV control as "revoke all", and the worker's refusal to
report a failure it could not justify — citing the component's own comment — is what
kept a false negative out of this document. The claim was then tested properly with
a third run.

Not shipped yet: finding 1 is a decision the owner made (name at pairing) that the
implementation only half-delivers, and shipping over it silently would leave the
feature doc claiming a capability the UI does not have.
