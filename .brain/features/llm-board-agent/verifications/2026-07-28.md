# Verification: LLM Board Agent — spend caps (issue #1)

- **Slug**: `llm-board-agent` (feature memo: `.brain/features/llm-board-agent/llm-board-agent.md`)
- **Date**: 2026-07-28
- **Verified by**: main thread — throwaway `bun` scripts driving the live dev server over HTTP (no browser; the surface under test is a tRPC error code and an HTTP status, not a rendered view)
- **Base URL**: http://localhost:5176 _(dev server: started by agent; 5173–5175 were occupied)_
- **Role**: owner (`admin@preview.local`, seeded) plus three unauthenticated paired "phones" holding only controller grants
- **Verdict**: ✅ PASS — **scoped to the spend caps only.** The feature's own golden path (voice → Whisper → `claude-sonnet-5` → board) is **NOT** verified here and feat-009 stays in-progress. See "What this does not cover".

## Scope

This verifies issue #1 — that `board.generate` and `/api/transcribe` are no longer
unbounded — and nothing else. Four claims, each measured against a real
`BoardRoom` Durable Object over the wire.

## Golden path

| # | Step | Expected | Observed | Result |
|---|------|----------|----------|--------|
| 01 | Sign in as the seeded owner | 200 + session cookie | `sign-in: 200`, 107 cookie chars. First attempt was `403 MISSING_OR_NULL_ORIGIN` — Better Auth requires an `Origin` header; a script artefact, not an app defect | ✅ |
| 02 | Create a board | 200 + board id | `3bf71fde-7e2c-4645-954d-896d9867a3b7`, `grantEpoch: 0` | ✅ |
| 03 | Call `board.generate` 21× sequentially (spender limit 20) | Attempts 1–20 pass the cap, 21 refused | Exactly that. Attempt 21: `TOO_MANY_REQUESTS` — *"Board generate limit reached. Try again in 1484s."* | ✅ |
| 04 | Read the wait back | A sane remainder of the hour window | `1484s` — consistent with a fixed 3600s window entered ~35 min earlier | ✅ |

### The claim that justifies putting this in the Durable Object

| # | Step | Expected | Observed | Result |
|---|------|----------|----------|--------|
| 05 | Fire **30 concurrent** `board.generate` calls at a fresh board, limit 20 | At most 20 admitted — a racy counter would let more through | `{ INTERNAL_SERVER_ERROR: 20, TOO_MANY_REQUESTS: 10 }`. **Admitted: exactly 20.** No increments lost | ✅ |

`INTERNAL_SERVER_ERROR` is the *expected* success shape here: `ANTHROPIC_API_KEY`
is absent locally, so a call that clears the cap then fails at the model. That it
fails *after* being charged is the ordering the code intends — the cap is checked
before the paid call, so the 20/10 split is read as "20 cleared the cap".

### Per-spender fairness

| # | Step | Expected | Observed | Result |
|---|------|----------|----------|--------|
| 06 | Owner, one more call on the exhausted board | Refused | `TOO_MANY_REQUESTS` | ✅ |
| 07 | Mint a pairing token from the TV display HTML and redeem it with **no session cookie** | A controller grant | 195-char token; grant obtained holding no session | ✅ |
| 08 | Drive `board.generate` with only that grant | Its **own** 20, not the owner's exhausted bucket | Admitted 20, refused at 21 | ✅ |

### The re-pairing bypass (why the board ceiling exists)

| # | Step | Expected | Observed | Result |
|---|------|----------|----------|--------|
| 09 | A 3rd fresh grant on the same board (board at 40/60) | 20 more, landing the board on exactly 60 | `3rd grant admitted: 20 — board now 60/60` | ✅ |
| 10 | A **4th** fresh grant — brand-new nonce, zero personal spend — first call | Refused by the board ceiling, not the spender bucket | `4th grant, very first call: TOO_MANY_REQUESTS` | ✅ |

Step 10 is the whole argument for the second bucket: per-spender alone is
bypassable by re-pairing, because every redemption mints a fresh nonce and
therefore a fresh allowance. Re-pairing now buys nothing.

## What this does not cover

Stated plainly so nobody reads this doc as more than it is:

- **The feature's actual golden path.** Voice → Whisper → `claude-sonnet-5` →
  board is still unverified end to end. `ANTHROPIC_API_KEY` is not set in this
  worktree and the `AI` binding always hits remote Cloudflare. **feat-009 stays
  in-progress.**
- **`/api/transcribe`'s 429.** The same `spendQuota` call and the same ledger,
  but reaching it needs the `AI` binding, so only the `generate` endpoint was
  driven live. The transcribe path is covered by unit tests and by shared code,
  not by measurement.
- **Fail-closed on a broken ledger.** Unit-tested at the service boundary
  (`spendQuota fails closed when the room 500s` / `on an unrecognised ledger
  payload`), not induced against a live DO.
- **Window rollover.** The 3600s window was never crossed; `retryAfter`
  arithmetic is unit-tested.

## Findings for main thread

- `INTERNAL_SERVER_ERROR` on a missing `ANTHROPIC_API_KEY` is coarse. A caller
  cannot tell "the deployment has no key" from "the model broke". Not in scope
  for issue #1, worth a `ConfigurationError` later.
- A generation that fails *after* clearing the cap still consumes allowance.
  Correct for a genuine upstream failure; slightly unfair when the cause is a
  missing key. Left as-is — refunding on failure invites a retry loop that spends
  real money.

## Verdict rationale

PASS on the four claims issue #1 turns on: the cap bites at the right count, it
reports a usable wait, it does not lose increments under 30-way concurrency
(the reason it lives in the Durable Object rather than anywhere else), each
spender gets a separate allowance keyed by their grant's nonce, and a fresh
nonce cannot escape the board ceiling. All four were measured over the wire
against a real DO, not reasoned about. The verdict is deliberately scoped: this
says the endpoints are bounded, it does not say the LLM feature works.
