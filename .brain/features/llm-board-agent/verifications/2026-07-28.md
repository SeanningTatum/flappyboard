# Verification: LLM Board Agent — spend caps (issue #1) + pre-PR review round

- **Slug**: `llm-board-agent` (feature memo: `.brain/features/llm-board-agent/llm-board-agent.md`)
- **Date**: 2026-07-28
- **Verified by**: coordinator (Opus) delegating browser walks to worker sub-agents (Sonnet) driving the Playwright CLI; plus throwaway `bun` scripts for the protocol-level claims
- **Base URL**: http://localhost:5173 → 5176 → 5177 across rounds _(Vite auto-bumps; dev server started by agent)_
- **Role**: owner (`admin@preview.local`, seeded) plus paired "phones" holding only controller grants
- **Verdict**: ✅ PASS — enforcement and the refusal UI both verified. **Scoped:** this covers the spend caps, not the voice→board golden path.

## Round 1 — enforcement (protocol level)

Four claims, each measured over the wire against a real `BoardRoom` Durable Object.

| # | Claim | Observed | Result |
|---|-------|----------|--------|
| 01 | The cap bites at the right count | Refused at attempt 21 of 21. `"Board generate limit reached. Try again in 1484s."` | ✅ |
| 02 | **Atomicity** — 30 concurrent calls at a limit of 20 | `{ INTERNAL_SERVER_ERROR: 20, TOO_MANY_REQUESTS: 10 }` — exactly 20 admitted, no increments lost | ✅ |
| 03 | Per-spender fairness | Owner exhausted at 20; a phone holding **only** a redeemed grant and no session then got its own full 20, refused at 21 | ✅ |
| 04 | The re-pairing bypass is closed | A 3rd grant took the board to 60/60; a **4th** grant — brand-new nonce, zero personal spend — was refused on its **very first call** | ✅ |

Claim 02 is the one that justifies putting the counter in the Durable Object
rather than anywhere else. `INTERNAL_SERVER_ERROR` is the expected *success*
shape locally: `ANTHROPIC_API_KEY` is absent, so a call that clears the cap then
fails at the model — the app warns about this at startup.

## Round 2 — the refusal UI (browser, 3 independent runs)

Three workers drove the live controller at 390×844 on a board already at its
owner cap. **All three agreed**, and all three independently found the same
defect:

| # | Step | Observed (all 3 runs) | Result |
|---|------|------------------------|--------|
| 05 | Sign in → `/dashboard` | Clean | ✅ |
| 06 | Load `/b/:boardId/c` | Controller renders; VOICE "Hold to talk" is the only LLM entry point (no text-prompt control) | ✅ |
| 07 | **Golden path** — manual write at cap | `CAP TEST OK` sent, "SENT TO THE BOARD", revision advanced, history tagged `TYPED`. Plain writes are unmetered and unaffected | ✅ |
| 08 | **Error path** — hold to talk at cap | `/api/transcribe` 200, then `board.generate` **429**; revision did not advance and no `llm` history entry appeared — the cap fired before any model call | ✅ |
| 09 | What the user is told | **`"The board didn't take it. Try again."`** | ❌ **FAIL** |

Step 09 was a real defect in the change under review, not a test artefact.
`push-to-talk-button.tsx` discarded the error payload and always set
`{ kind: "generate" }`, so the static `control.voice.error.generate` string
rendered for a cap refusal exactly as for any other failure — while
`RateLimitError`'s own doc comment claimed `retryAfter` was there "so the phone
can say something better than 'try again later'". The sibling transcribe hop
*does* forward its server reason; generate did not. Workers drove real speech
through Chromium's fake-audio device to reach this, so the transcript hop was
genuine.

## Greptile review (pre-PR, on the committed branch vs `main`)

Ran clean this time — worth noting, because the same CLI hard-timed-out on this
repo's ~50-file MVP diff. Confidence 3/5. Four findings: 2 P1 escalated to the
human, 2 P2 auto-fixed.

| Pri | Finding | Resolution |
|-----|---------|------------|
| P1 | The DO read `spenderLimit`/`boardLimit`/`windowSeconds` off the request body and enforced them verbatim — the cap was a call-site convention, not a property of the enforcer | **Human chose: move policy into the DO.** Wire now carries only `endpoint`, `spender`, `mode`; a test asserts a caller cannot express a limit |
| P1 | Quota charged before `readBoundedBody`, so oversized **chunked** bodies burned slots at zero AI cost — 200 of them kill transcription for the household | **Human chose: peek → read → charge.** Read-only over-cap check before the body, real increment only after it validates |
| P2 | Corrupt counter silently reset to zero, unobservable | Logs a warning. Still fails *open* deliberately — bricking a family's board over bad bookkeeping is worse, and the other bucket bounds it |
| P2 | `windowSeconds` in storage keys — mismatched callers would see separate counters | Dissolved by the first P1 fix; the window comes from the policy now |

## Round 3 — after the fixes

Round 3a fielded two workers. One (run B) confirmed the new copy. The other (run
A) came back **BLOCKED rather than confirming**, and the cause was mine: my own
transcribe-cap proof had exhausted the *transcribe* bucket on the same board the
workers were using, so its voice press was refused at the wrong hop and never
reached `board.generate`. Run A declined to report the transcribe message as if it
were the thing under test, which is exactly right — one run is not a PASS, so the
round was re-fielded (3b) on a board with `generate` at cap and `transcribe`
untouched.

Run A also caught a real inconsistency while it was there: the transcribe route's
own 429 read `"Try again in 1065s."` — raw seconds, from a string I had added in
this same change, while the sibling generate copy said "21 minutes". Fixed with a
shared, tested `formatWaitEnglish`; that route renders its `error` verbatim on the
phone, so the wording has to be finished server-side.

  error.
- **networkErrors** — `429@step08` and `429@step10` are the refusals under test.

## What this does not cover

- **The feature's own golden path.** Voice → Whisper → `claude-sonnet-5` → board
  end to end. `ANTHROPIC_API_KEY` is absent here, so `generate` never reached the
  model; phase 6 was proven by a real call against the real account on
  2026-07-27, not by a screenshotted walk. Worth doing on real hardware alongside
  the Samsung TV walk `[[kiosk-display]]` owes.
- **Fail-closed against a live broken DO.** Unit-tested at the service boundary
  (500 and unrecognised-payload both raise rather than permit), not induced live.
- **Window rollover.** No run crossed the 3600s boundary; the arithmetic is
  unit-tested.
- **The `zh` refusal copy on screen.** Both strings exist and are asserted by the
  locale-parity test, but every browser run was in `en`.

## Findings for main thread

- No new `data-testid` gaps — workers found `control-row-input-0`, `control-send`
  and `control-ptt` without trouble.
- Harness note for future walks, from run C: the PTT button can sit below the
  fold at 390×844, and driving `mouse.move/down/up` at off-screen coordinates is a
  **silent no-op** — no request, no error. `scrollIntoViewIfNeeded()` before taking
  the bounding box fixes it. Worth knowing, because the failure looks exactly like
  "the feature did nothing".
- A generation that fails *after* clearing the cap still consumes allowance.
  Correct for a genuine upstream failure, slightly unfair when the cause is a
  missing key. Left as-is: refunding on failure invites a retry loop that spends
  real money.
- No committed e2e spec was added for the cap. Deliberate, per feat-006's rule
  that browser verification replaces per-feature e2e specs and the committed
  suite stays a thin smoke net — a 20-call e2e would be slow and flaky for little
  signal. The regression is pinned by unit tests instead: `voiceCopyKey` now
  proves a cap refusal and a generic failure resolve to *different* keys, in both
  locales.

## Verdict rationale

PASS. Enforcement was measured, not reasoned about: the cap bites at the right
count, does not lose increments under 30-way concurrency, gives each spender a
separate allowance, and cannot be escaped by re-pairing. The refusal UI was
verified by **three** independent runs after the fix — on two different fixtures,
against three different `retryAfter` values the server actually sent — and runs C
and D confirmed the 429 came from `board.generate` with `/api/transcribe`
returning 200, so it is the cap under test and not a decoy refusal upstream. The
two P1 review findings were fixed to the human's stated choices, and the more
serious of them — the free budget drain — was re-measured closed rather than
assumed. The one defect this round found that no static review did (a cap refusal
rendering generic copy) is fixed and pinned by tests.

Two of this round's corrections were to my own work rather than to the code under
review: I contaminated a fixture and blocked a run, and I shipped a raw-seconds
string in the same change that fixed a raw-seconds problem next door. Both are
recorded above rather than quietly re-run, because the first number a test gives
you is not automatically the true one.

The verdict is scoped: this says the endpoints are bounded and the refusal is
legible, not that the LLM feature works.
