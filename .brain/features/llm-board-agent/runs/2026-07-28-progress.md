## Step 3 — Enabled the server-side web_search tool on board.generate so live-data prompts (weather, scores, prices) put real numbers on the board instead of a training-cutoff guess.

_(Was Step 1 of the web-search track, PR #4.)_

```
Verified against the live API before writing any code, because the docs do not state whether server tools and structured outputs coexist: claude-sonnet-5 + web_search_20260318 + output_config.format json_schema returned stop_reason=end_turn with a single schema-valid JSON text block, and the dynamic-filtering code_execution blocks appeared without code_execution being declared. Three response-shape consequences had to be handled: (1) the JSON is the TRAILING text run, since a searching response interleaves server_tool_use/web_search_tool_result/code_execution_tool_result blocks and the model may narrate first — joining all text blocks would feed JSON.parse a sentence glued to an object; (2) stop_reason pause_turn now reachable, resent unchanged and deliberately NOT charged a retry attempt; (3) retries now echo response.content verbatim rather than the extracted text, because web search results carry encrypted_content the API decrypts to restore them (echoing text alone silently re-searches, and drops thinking blocks that must be replayed unmodified). max_uses=3 bounds cost and wait; max_tokens 4096 to 8192 for the extra output blocks. End-to-end on the real prompt and schema: 'weather in oslo' produced OSLO WEATHER / NOW 14C 57F / SKY MOSTLY CLOUDY / WIND 6 MPH in one attempt with no repair (~31s, two searches); 'bin day is thursday' correctly did not search (~10s). 855 unit tests green (6 new), typecheck clean.
```
