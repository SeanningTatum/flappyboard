
I have written this up in rules/services.md as a third pattern ("Secrets are not bindings"), with the decision rule: binding always declared -> global runtime; binding may be absent and consumer is a route -> ad-hoc; secret may be absent and consumer is a procedure -> global runtime but degrade instead of failing. ## Step 8 — User photographed a real weather board showing three inconsistent layout failures; diagnosed the root cause and delegated a structural fix rather than a prompt tweak.

```
Observed on the TV: TEMP...18C was flush to column 23 (correct), but RAIN...30% and AIR QUALITY...GOOD both stopped ~3 columns short, and SKY / CLOUDY split across two rows. Root cause confirmed by grep — the word spread appears NOWHERE in app/lib/schemas/board.ts or app/lib/board/compile.ts. It exists only as an editor concept in segment-layout.ts, which pre-resolves it into a left-aligned row with computed gap spaces before a BoardMessage is built, so BoardAlign is only left|center|right and the LLM JSON SCHEMA CANNOT EXPRESS SPREAD AT ALL. The model therefore hand-pads with literal spaces: occasionally it counts right (18C), usually not (30%, GOOD), and when its padding pushes a row past 24 columns the compiler word-wraps the overflow onto the next row — which is exactly the SKY/CLOUDY split. So this was never a prompt-wording problem: layout lived in two places and the model could only reach the weaker one, which also contradicts the feature docs own claim that the compiler owns all layout.
```
