- **Slug**: `phone-control` (feature memo: `.brain/features/phone-control/phone-control.md`)
- **Date**: 2026-07-27
- **Verified by**: feature-verifier (Playwright CLI — throwaway headless script run with `bun run tmp/verify-phone-control.ts`, bundled chromium, `--disable-extensions`, fresh profile)
- **Base URL**: http://localhost:5173 _(dev server: started by agent — an existing 22-minute-old `react-router dev` on :5173 was stopped and replaced so the worker + DO code under test was known-fresh; `bun run db:seed` re-applied the fixtures)_

- **Board**: `seed-board` ("Demo Board"), owned by the admin fixture
- **Verdict**: ✅ PASS — a phone with no session and no account paired off the TV's QR token and drove the board end to end (send, sound pack, mute, history re-flip); a replayed token and a bare visit both land on the rescan prompt with no grant issued. Zero jsErrors, zero networkErrors.

## Console

Collected on **every** page in the run (TV, phone, and both error-path contexts) via `pageerror` + `console` + `response` listeners, with each network entry tagged by the step it fired in.

- **jsErrors**: **none.**
- **networkErrors**: **none** — including on E1 and E2, where a 4xx would have been *expected and allowed*. There is none because both refusals are decided server-side: the `/b/:boardId/c` loader calls `board.pair` / `board.claim` through the in-process `context.trpc` caller and answers with a 302 to the clean URL (E1) or a 200 rendering `RescanPrompt` (E2), so no failing HTTP request ever reaches the browser.

### Two harness artifacts encountered and eliminated (neither is an app defect)

Recorded because both would read as app bugs to the next person who runs this.

1. **`caret-color: transparent` hydration mismatch on the phone.** An intermediate run logged a React "tree hydrated but some attributes… didn't match" warning whose only diffed style was `caret-color: transparent` on all six row inputs. Grep evidence: `grep -rn "caret-color\|caretColor\|caret_color" app/` → **absent from `app/` entirely**; the string lives in `node_modules/playwright-core/lib/server/screenshotter.js:72`, which does `element.style.setProperty("caret-color", "transparent", "important")` on every `input,textarea,[contenteditable]` before a screenshot. My screenshot was racing hydration on a streamed RRv7 page. Fixed in the driver by gating each screenshot on real hydration (waiting for a `__reactFiber$` key on `control-root` / `board-display`) and passing `caret: "initial"`. The final run — deliberately started with the board already `muted=1`, the exact SSR state that had produced the warning — is clean. **Environment artifact, not a FAIL.**
2. **Vite dep-optimizer 504s on a cold dev server.** The first attempt hit `504` on `/node_modules/.vite/deps/{effect,lucide-react,@hookform_resolvers_effect-ts}.js`, which broke hydration, so the login `<form>` submitted natively and returned `405`. Cured by loading `/login` and `/b/seed-board/c` twice to let Vite prebundle, then re-running. Dev-server warm-up only — it cannot occur against a built worker.

## Findings for main thread

- **No defects found.** Every testid named in the brief exists and behaves as documented.
- Testid naming worth knowing before writing more automation (not a bug, just non-obvious): `control-row-<n>` is the **`FormItem` wrapper** and is **0-indexed**, while the visible label is 1-indexed. The `<input>` itself is `control-row-input-<n>`; swatches are `control-row-<n>-color-<color>`; alignment is `control-row-<n>-align-<align>`; history buttons are `control-history-entry-<revision>` (keyed by revision, not by index).
- The TV exposes no `data-muted`/`data-sound-pack` on `board-display`, so "the TV received the mute" is not readable from the DOM. I proved it by capturing the TV's WebSocket frames (`{"type":"state","revision":42,…,"muted":true}`). That is sufficient and arguably the better assertion — but if the intent is for a plain DOM assertion to be possible, `board-display` would need those attributes. Flagged, deliberately **not** changed.
- **Test-data hygiene, not a code issue:** the local `board_snapshot` table for `seed-board` is dominated by blank-grid revisions (21–41) from earlier runs, and `board.revision` has drifted to 44. Any future verification that wants to re-flip a *recognisable* history entry must create it in-run (this run sent an interim message for exactly that reason) or re-seed. `bun run db:seed` uses `INSERT OR IGNORE`, so it will not reset the drifted board row.
- Side effect of this run, left in place: `seed-board` ends `muted=1`, `sound_pack=classic`, revision 44, showing `HELLO TV 7061 / PHONE CONTROL`. Harmless — the driver normalises mute at the start of step 05.

## Verdict rationale

**PASS.** The feature's central claim is that a phone with no account can take over the board by scanning the TV, and that is exactly what was demonstrated rather than assumed: the controller context was asserted to hold zero cookies before navigating, and after pairing it held one `HttpOnly` `fb_grant_seed-board` cookie and **no session cookie**, yet from that state it sent a message that flipped the TV's tiles (verified by reading `data-char`/`data-color` off the TV's own `flap-tile` nodes, `data-revision` 41 → 42), changed the sound pack, muted the board, and re-flipped an earlier history entry (43 → 44). The revision semantics behave as the code claims: a **grid write increments** the revision, a **settings write does not** — the TV's socket received a `state` frame carrying `revision: 42` with `muted: true`, and both the TV's `data-revision` and its rendered grid were unchanged across that write, which is precisely what `shouldApplyState`'s "apply equal revisions" rule exists to allow. Both error paths degrade into the same instruction rather than an error: replaying the step-02 token was refused with no grant issued (the DO-backed single-use ledger held) and the token was stripped from the URL even on the failure branch, and a bare no-grant visit rendered `control-rescan` with `board-error` absent. Console was empty on all four contexts; the one hydration warning seen mid-investigation was traced by grep to Playwright's own screenshotter injecting `caret-color: transparent` (`app/` contains that string nowhere) and disappeared once screenshots were gated on hydration, including on a re-run deliberately started in the SSR state that had triggered it.
