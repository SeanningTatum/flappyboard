## Error path

_The WebSocket dies with HTTP still up (Playwright `routeWebSocket` proxying
`/api/board-ws` from page load; the kill closes both halves of the live pair and
refuses every reconnect). The board must show the scrim over the retained grid,
hard-reload exactly once past `WATCHDOG_MS` (2 min), never reload again, and
recover when the socket comes back._

Reloads were counted by an `addInitScript` counter persisted in `sessionStorage`
(incremented on every page load, exposed as `window.__reloadCount`), so a count
of 2 means "initial load + exactly one reload".

| E4 | Unblock the socket, send `BACK ONLINE 7` | board live again, scrim gone, fresh message flaps | `data-status="live"`, scrim gone, `data-revision` 1 → 2 in 508ms | [`E4-recovered.png`](../screenshots/E4-recovered.png) | ✅ |

E3 is the finding this feature exists to avoid. `shouldReload`
(`app/lib/board/kiosk.ts:138`) is correctly gated on a `reloaded` flag, and the
unit test "never reloads twice" passes `reloaded: true` explicitly — but the
flag is `const reloaded = useRef(false)` in `app/routes/board/display.tsx:258`,
so `window.location.reload()` itself resets it. With the socket still dead, the
fresh page sets `downSince` at mount and reloads again ~2 minutes later:
measured twice, 120,961ms and 120,940ms — a slow reload loop for as long as the
outage lasts, the exact failure mode `kiosk.ts`'s doc comment calls "strictly
worse than a stale board". Persisting the spent reload (e.g. `sessionStorage`)
is the obvious fix; **reported, not fixed** — no app code was touched.

## Findings for main thread

1. **The one-shot watchdog loops across its own reload (the FAIL above).**
   `reloaded` must survive `window.location.reload()` to mean "exactly one
   reload, ever" — e.g. a `sessionStorage` flag read when initialising the ref.
   Timing evidence: reloads at +120,961ms and +120,940ms after the socket
   died / after the previous reload, i.e. the loop period is the full
   `WATCHDOG_MS` each time.
2. **A wedged-open-but-dead socket is invisible to both the scrim and the
   watchdog.** In run 2, only the server half of the proxied socket was closed:
   the page's socket stayed `OPEN`, `data-status` stayed `"live"`, no scrim
   ever appeared, and no reload ever fired (210s observed) — while the board
   silently received nothing. The watchdog keys off `useBoardSocket`'s
   `status`, which only moves on close/error events. The feature doc names "a
   socket wedged open but dead" as a case the watchdog exists for; as built,
   only the visibility-resume resync path (`RESYNC_TIMEOUT_MS`) can detect a
   wedge, and only when the tab is hidden and reshown. Worth a decision: either
   scope the doc's claim to *detectable* socket death, or add an application
   -level heartbeat.
3. **Harness notes for future kiosk walks (not app defects):** patching
   `window.WebSocket` in an `addInitScript` bypasses Playwright's
   `routeWebSocket` instrumentation — the kill in run 1 silently didn't hold
   and the board reconnected (this is why run 1's "no reload" was a test bug,
   not an app pass). The working pattern is to proxy the socket with
   `routeWebSocket` from page load and close **both** halves of the live pair;
   closing only the server half produces finding 2's wedge instead of a
   detectable death.
4. Leftover: three `kiosk-verify-20260729-r*` boards exist in the **local** D1
   from the three runs; harmless, delete via `/boards` if unwanted.

## Verdict rationale

FAIL. Every measured claim passed except the one the feature doc states in
bold: "Exactly one reload, ever." With the socket held dead, the display
hard-reloaded at +121s (correct), then reloaded **again** at +121s after that
(disproving the one-shot), because the gate that makes `shouldReload` one-shot
lives in a page-lifetime ref that the reload itself discards. The loop is slow
(one reload per watchdog window, not a hot loop) and recovery after unblocking
works, so the board is not bricked — but the shipped behaviour contradicts the
feature's central anti-reload-loop guarantee, and the fix belongs in app code,
not in this doc. Everything else — 144 tiles, 24×6, `scrollable=false` with
drift observed ticking at the 4-minute interval, transform-not-layout drift,
`data-dimmed` correct for the hour, scrim-over-retained-grid, watchdog timing,
clean recovery, zero console errors — passed with measured evidence.

## Re-test after the latch fix (walk 2)

Same date, same verifier, same method (fresh dev server on http://localhost:5191,
seeded owner, fresh board `kiosk-verify-20260729-w2` / `da55b393-…`, real
content `LATCH CHECK 88` on the grid before any kill). The fix under test: the
page-lifetime `useRef` latch is gone from `app/routes/board/display.tsx`;
`app/lib/board/kiosk.ts` now ships `createReloadLatch(storage)` — a
sessionStorage-backed latch (`flappyboard:watchdog-reloaded`) that survives
`window.location.reload()`, blocks `shouldReload` while latched, and is cleared
whenever the socket is observed `live`.

**Harness non-interference, stated explicitly because the latch now lives where
the counter lives:** the reload counter uses sessionStorage key `kioskReloads`
(≠ the app's latch key), the init script never calls `sessionStorage.clear()`
or `removeItem`, and nothing else in the harness touches storage — so the
app's latch persisted and cleared exactly as designed, and what was measured is
the app, not the harness.
