## Keyboard, targets, reduced motion, `zh`

Driven at 390×844 after the fixes below. **Read after a 400ms settle, never on the frame `Tab` lands** — Tailwind v4 includes `outline-color` in `transition-colors`, so an immediate read reports `currentColor` mid-fade. That artifact made four segmented controls look as though they painted a #151515 outline on a black field. None of them did. The fifth finding — the text inputs — survived the re-measure and was real.

| Check | Result |
|---|---|
| Focus ring, `/boards` | 5/5 stops paint `2px solid rgb(255,204,0)` |
| Focus ring, `/link` | 1/1 |
| Focus ring, controller | 14/14, **including all six typing wells** |
| Targets ≥44px | all stops pass |
| `zh` — `/boards`, controller, `/link`, `/tv` | no raw dotted keys rendered, no horizontal overflow (390/390) on any |
| Reduced motion | `design:audit` reports 0 animated → 0 under `prefers-reduced-motion` on every surface |

**Two real defects, found here and fixed in this PR:**

1. **Every text input in the app had no focus indicator.** `input.tsx`'s base class carried `outline-none`, which emits `outline-style: none` and kills both the global `:focus-visible` outline and its forced-colors fallback — the identical defect fixed in `button.tsx` during phase 1 and missed here. What remained was `focus-visible:ring-*`, a `box-shadow`, and the controller's six wells overwrite `box-shadow` inline with `WELL_LIP`. Measured `outline: 0px none` with only the well lip in the shadow. Login and sign-up were in the same state. Removed from `input.tsx` and `textarea.tsx`.
2. **Three controls below the 44px floor** on the phone: paint mode 60×36, add-segment 78×32, alignment keys 84×36. Raised to `h-11`.

**Not a defect, recorded so it is not re-litigated:** the `zh` rack still shows board *names* in Latin flaps. The board's charset is Latin-only by construction (`BOARD_CHARS`), so a CJK board name folds away — the surrounding UI is fully translated, which is what the parity test guards.

## Design critique — three rounds

`design-critic` judges the render, never the source, and its verdict is blocking. It returned **DO NOT SHIP twice**. Both times it was right, and both times part of what it found was invisible to every other gate in this document — typecheck, unit tests, e2e, the browser walk and `design:audit` all passed on renders it rejected.

**Round 1 → DO NOT SHIP, six P1s.** Confirmed two of the three blockers carried over from the phase-1 verdict as resolved *in the pixels* (the pigments are spent; the app and hardware surfaces read as one product) and called the third partial. New: `/link` was the only screen with no product on it — "cover the wordmark and it is Netflix's TV pairing"; the card had been restyled rather than removed; the mute `Switch` was the only pill and the only circle in a 0px-radius product *and* read backwards, since `checked` meant muted; nothing anywhere exceeded ~20px, so the wordmark, the page title and a board's name were peers; the app never used its own voice on itself; and the disabled SAVE key composited to a flat mid-grey found nowhere else.

**Round 2 → DO NOT SHIP, four P1s**, and it **refuted part of round 1's fix**: `/link`'s caret only painted while focused, so at rest six unlit tiles measured **1.15:1** against their plate — no way to see it was a field. It also caught that the 44px sweep in this document had never reached the pigment swatches (31×32 with 5px gaps), that three different encodings of "selected" now coexisted, and that the de-carding had landed on Settings only.

**What the mechanical gates could not see, and why:**

| Defect | Why the gate missed it |
|---|---|
| `/link` field at 1.15:1 | `design:audit`'s 10.16:1 body-contrast pass never looked at it — the field holds **no text** at rest |
| 31×32 swatches | the focus walk tabs through 14 stops and never reaches them |
| Three "selected" encodings | every one of them passes contrast and target size individually |
| Mute switch reading backwards | `aria-checked` was correct; the *semantics* were inverted |

**Round 3 → SHIP.** No P0, no P1. All eight round-2 items verified against the pixels, with numbers: `/link`'s slot bars measure 5.2:1 empty and 15.9:1 on the next cell; the swatches are 64×48 CSS at 8px pitch; one encoding of "selected" survives across all five segmented controls; the pinned action bar's bottom edge lands at CSS y=841 of an 844 viewport. Its verdict on the whole: *"the split-flap module is the atomic UI primitive, not a picture of one — one idea carried structurally through every surface at four scales."*

Seven P2s and six P3s remained at that point. Taken in a final pass: the label left-rule stagger, the last nested container (`PAIRED DEVICES`), `/link` being vertically centred with no exit (it re-centred under the thumb when the keyboard opened, and a refused code left only the browser gesture), the copy key at 39px against a 44px floor, and the code field's plate moved to the well tone.

**Refuted, with the reason:** the blank eighth swatch reads as a missing item to a critic but is correct — `white` and `black` share a fill on the real object, so `white` is *a white glyph on an unlit flap* and `black` is *an unlit flap*. Drawing a glyph on it would make the two indistinguishable, which is the defect the blank exists to prevent.

**Deliberately not taken, and recorded as owed rather than fixed:** desktop composition (a 416px column centred in 1440 with no adaptation — the rack is the one screen with content worth arranging at width), `/tv` at 1440 (the code strip is ~250px on a screen meant to be read across a room), and two copy repeats. All P2, none of them phone-first, and the desktop pass is properly its own piece of work. Also owed: the row inspector opens below the fold when summoned in paint mode (needs a scroll-into-view), and white carries both "current" and "commit" — a second lit weight would separate them, but that is a token decision rather than a fix.

## Findings for main thread

- **The QR-scan happy path is not driven here.** It needs a real second device holding the TV's socket; this walk covers the typed-code fallback and the refusal. The scan path's server logic is unchanged except that `resolveAutoLink`'s branch was deleted, and the loader and the action now share one `pairNewBoard`, so both halves take the identical code path — the typed submit above exercises it.
- **Tizen.** `FlapWord` states its size as explicit width/height derived from one cell width rather than `aspect-ratio` (Chromium 88; the Tizen panel is 56), because a grid with no intrinsic height collapses to nothing there. **Not verified on real hardware** — this is reasoning from the constraint already documented in `flap-tile.tsx`, and the physical-TV check the plan asks for is still owed.
- The armed-in-place pattern replaced four Radix `AlertDialog`s. Anything that later wants a confirm on a console surface should use `ArmedKey`, not reach back for the dialog.
