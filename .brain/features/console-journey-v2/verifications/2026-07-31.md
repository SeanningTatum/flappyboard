## Keyboard, targets, reduced motion, `zh`

Driven at 390×844 after the fixes below. **Read after a 400ms settle, never on the frame `Tab` lands** — Tailwind v4 includes `outline-color` in `transition-colors`, so an immediate read reports `currentColor` mid-fade. That artifact made four segmented controls look as though they painted a #151515 outline on a black field. None of them did. The fifth finding — the text inputs — survived the re-measure and was real.

| Check | Result |
|---|---|
| Focus ring, `/boards` | 5/5 stops paint `2px solid rgb(255,204,0)` |
| Focus ring, `/link` | 1/1 |
| Focus ring, controller | 14/14, **including all six typing wells** |
| Targets ≥44px | all stops pass |
| `zh` — `/boards`, controller, `/link`, `/tv` | no raw dotted keys rendered, no horizontal overflow (390/390) on any |
| Reduced motion | `design:audit` reports 0 animated → 0 under `prefers-reduced-motion` on every surface |

**Two real defects, found here and fixed in this PR:**

1. **Every text input in the app had no focus indicator.** `input.tsx`'s base class carried `outline-none`, which emits `outline-style: none` and kills both the global `:focus-visible` outline and its forced-colors fallback — the identical defect fixed in `button.tsx` during phase 1 and missed here. What remained was `focus-visible:ring-*`, a `box-shadow`, and the controller's six wells overwrite `box-shadow` inline with `WELL_LIP`. Measured `outline: 0px none` with only the well lip in the shadow. Login and sign-up were in the same state. Removed from `input.tsx` and `textarea.tsx`.
2. **Three controls below the 44px floor** on the phone: paint mode 60×36, add-segment 78×32, alignment keys 84×36. Raised to `h-11`.

**Not a defect, recorded so it is not re-litigated:** the `zh` rack still shows board *names* in Latin flaps. The board's charset is Latin-only by construction (`BOARD_CHARS`), so a CJK board name folds away — the surrounding UI is fully translated, which is what the parity test guards.

## Findings for main thread

- **The QR-scan happy path is not driven here.** It needs a real second device holding the TV's socket; this walk covers the typed-code fallback and the refusal. The scan path's server logic is unchanged except that `resolveAutoLink`'s branch was deleted, and the loader and the action now share one `pairNewBoard`, so both halves take the identical code path — the typed submit above exercises it.
- **Tizen.** `FlapWord` states its size as explicit width/height derived from one cell width rather than `aspect-ratio` (Chromium 88; the Tizen panel is 56), because a grid with no intrinsic height collapses to nothing there. **Not verified on real hardware** — this is reasoning from the constraint already documented in `flap-tile.tsx`, and the physical-TV check the plan asks for is still owed.
- The armed-in-place pattern replaced four Radix `AlertDialog`s. Anything that later wants a confirm on a console surface should use `ArmedKey`, not reach back for the dialog.
