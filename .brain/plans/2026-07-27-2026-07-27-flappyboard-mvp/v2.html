flappyboard MVP

2026-07-27 · features: split-flap-board, phone-control, llm-board-agent · in-review · round 1

TL;DR

A 6×24 split-flap board renders full-screen on the TV and is driven live from a phone that pairs by scanning a QR code — no login on the phone. State lives in one Durable Object per board and pushes over WebSockets, so a flip on the phone lands on the TV in well under a second. The headline feature is walkie-talkie mode: hold to talk, Whisper transcribes, claude-sonnet-5 returns a schema-constrained board message, and an Effect Schema decode plus deterministic repair pass guarantees a renderable 6×24 grid every time — the board never breaks because the model got creative.

Round 1: all six decisions are answered and all six open questions are closed — see Decisions and Resolved. The three changes that rippled into the plan: the TV is a Samsung Tizen browser (so conservative CSS, an audio-unlock gesture, and wake-resync are now acceptance criteria), flap SFX ship as a selectable sound pack with a mute toggle on the phone, and the schema is multi-board from day one while the UI ships a single board.

Decisions needed

All six are answered in round 1 — the chosen option stays pre-selected on each card. Re-queue any card to change your mind.

1. How do the TV and phone stay in sync? Durable Object + WS The TV is a passive display; the phone is the writer. Both need the same grid within a moment of any change.

OptionProsCons
Single authoritative writer, sub-100ms push, no polling cost, hibernation means an idle board costs nothing; SQLite-backed DOs are on the Workers free plan New binding + a migrations block in wrangler.jsonc; one more runtime concept in the codebase
Zero new bindings, works with the tRPC layer exactly as it exists today Up to 1s of visible lag on every flip, ~86k reads/day per idle board, and manual-edit feedback feels laggy on the phone
One-way push, no DO Doesn't actually work — each request may hit a different isolate, so there's no shared fanout point to broadcast from

2. What shape is the board data the LLM produces? semantic segments This is the single highest-leverage decision in the plan — it determines how often the model can produce something unrenderable. 6×24 = 144 cells.

OptionProsCons
~10× smaller output, so far fewer tokens and far fewer ways to be wrong; the compiler owns wrapping, centering, charset legality and the 6×24 invariant, so the grid is correct by construction; still gives per-word and per-block color Can't express arbitrary per-cell pixel art
Total control, per-cell color, pixel art possible 144 objects per response; the model must count to 24 six times — the most common structural failure mode, and the expensive one to retry
Covers art/patterns later without giving up the safe default path Two code paths and two validators to test from day one
What "rows of colored segments" looks like 
{ "rows": [
    { "align": "center", "segments": [ { "text": "GOOD MORNING", "color": "yellow" } ] },
    { "align": "center", "segments": [ { "text": "SEAN", "color": "white" } ] },
    { "align": "left",   "segments": [ { "text": "  ", "color": "red" },
                                       { "text": " 3 MEETINGS TODAY", "color": "white" } ] }
  ] }

A segment of pure spaces with a color is how you get solid color tiles — same primitive as a real Vestaboard's color chips. The compiler word-wraps each row to 24, applies alignment, upper-cases, maps unsupported characters, and emits exactly 6 × 24 cells. Rows omitted by the model become blank rows.

3. Which model generates the board? claude-sonnet-5 The task is small (a transcript in, a few rows of witty copy out) but it must respect a JSON schema and be fun to read. You picked Sonnet 5 over the recommended Opus 5 — noted and applied everywhere below; the row is marked so the tradeoff stays visible.

OptionProsCons
Same schema-enforced output_config.format path as Opus; near-Opus quality on this kind of short constrained copy; $3/$15 per MTok (intro $2/$10 through 2026-08-31) and noticeably faster time-to-flip, which matters when you're standing in front of the TV waiting for it Slightly less flair than Opus on open-ended "be witty" prompts
Best copywriting of the three $5/$25 per MTok and a slower round trip for a job Sonnet handles well
Binding already exists, no key, no egress, cheapest Weakest instruction-following of the three — the retry/repair loop would earn its keep more often

Two implementation notes that follow from picking Sonnet 5. It needs ANTHROPIC_API_KEY as a Worker secret (documented in .dev.vars.example, set via wrangler secret put — never process.env, per non-negotiable #5). And the model id is the bare string claude-sonnet-5 with no date suffix — it rejects temperature/top_p outright, so board "variety" comes from the prompt, not a sampling knob. The retry-and-repair loop in decision 4 stays regardless: schema enforcement stops malformed JSON, not a model that writes a 40-character line.

4. What happens when the model's output still doesn't fit? retry ×2 → repair You asked for a validator that retries until valid. The open question is what the last resort is.

OptionProsCons
The board always updates — bounded latency, bounded cost, and a repair pass (clip to 24, drop rows past 6, unknown colour → white) that is pure, synchronous and unit-testable A pathological response can render as clipped text rather than an error
Never shows a degraded board; failures are visible instead of silently absorbed Unbounded retries on a bad prompt, and a walkie-talkie that sometimes just does nothing is the worst possible UX for this product
Fastest and cheapest — one call, always Gives up the model's chance to fix its own mistake, so more clipped boards

In all three options the retry is Effect.retry with Schedule.recurs, the schema is Effect Schema (never Zod), and the failure is a tagged BoardGenerationError mapped in tagToTRPC. The repair pass also gets a fuzz test: a corpus of adversarial model outputs must all produce a valid 6×24 grid.

5. How does the phone earn the right to drive the board? signed pairing token The QR code is on a TV in a room — treat anything on screen as public.

OptionProsCons
No login on the phone (the whole point of scanning); token is HMAC-signed with BETTER_AUTH_SECRET, single-use, ~2 min TTL and rotates on the display; the grant is a scoped cookie the DO recognises, revocable from the TV One more token type to implement and test
Real identity per controller, reuses the shipped auth feature as-is Typing a password on a phone to change the words on your own TV; kills the scan-and-go experience
Simplest thing that could work; fine for a board in your own living room The URL is displayed on a TV — anyone who photographs it controls the board forever, with no way to revoke

6. How does hold-to-talk become text? Whisper upload Walkie-talkie is the headline feature, so this path has to work on the phone you actually own — iOS Safari.

OptionProsCons
Uses the AI binding that's already declared and has no consumers yet; identical behaviour on every browser; the audio blob is a fixture you can replay in tests Round-trip latency after release (upload + transcribe) instead of live text
Free, no upload, live interim transcript while you hold the button Support and quality vary by browser and OS version; nothing to replay in a test, so the feature-verifier can't drive it headlessly
Best latency where supported, correctness everywhere else Two transcription paths in the MVP — more surface than the first version needs

7. What runs the display — new in round 1. needs your answer You asked whether the Samsung TV's own browser is the right call or whether there's a better way. Short answer: start with the TV browser. It's zero hardware, it proves the product tonight, and Tizen's browser handles WebSockets and CSS transforms fine. The friction is operational, not technical — it won't auto-launch on power-on, the TV's power-saving can blank or suspend the tab, there's no remote way to reload it, and the engine trails desktop Chrome by a while. A cheap kiosk device fixes all four. My recommendation is to plan for the escape hatch rather than buy hardware up front.

OptionProsCons
No hardware, no setup, working board today; the conservative-CSS and wake-resync constraints already in Phase 3 are exactly what a kiosk device would want anyway, so switching later costs nothing Manual relaunch after the TV powers off; you may find the power-save blanking annoying
Auto-launches on power, never sleeps, a guaranteed modern engine, remotely manageable — the way a real always-on board should work ~$35–60 and an evening of setup before you see a single flip
Proper autostart, no browser chrome at all A whole second toolchain and a Samsung developer account to render a web page you already have

Plan of record

Six phases, three brain features. The scope policy allows one in-progress feature at a time, so they ship in order: split-flap-board (phases 1–3) → phone-control (phase 4) → llm-board-agent (phases 5–6). Every phase ends green on bun run typecheck && bun run test; the user-visible ones also need a feature-verifier PASS doc.

  1. Phase 1 — domain core, no UI and no network. Effect Schema for BoardMessage (rows of colored segments) and BoardGrid (6×24 cells), the charset table, the layout compiler (upper-case, word-wrap to 24, align, map unsupported chars), and the repair pass. Acceptance: unit tests cover compiler and repair; a fuzz corpus of adversarial model outputs all produce a structurally valid 6×24 grid; no Zod anywhere.
  2. Phase 2 — persistence and the realtime room. D1 tables board + board_snapshot with a Drizzle migration and an Effect.Service BoardRepository — board carries ownerId and a name so several boards per account are a data reality from day one, even though the UI ships one; the BoardRoom Durable Object with WebSocket hibernation, one DO per boardId, and last-write-wins on a monotonic revision; BOARD binding plus a migrations tag in wrangler.jsonc for both the default and preview env; tRPC board.get / board.setMessage / board.history. Acceptance: two browser tabs on the same board, a write in one appears in the other in under 300ms; two different boardIds stay fully isolated; repository unit-tested; bun run build passes (catches Workers-compat breakage).
  3. Phase 3 — the TV display. Route /b/:boardId renders 144 flap tiles at full-bleed with a CSS flip animation and per-cell color, subscribes over WebSocket, plays a flap SFX from the selected sound pack, and overlays a QR code that encodes the current pairing token. Targets the Samsung TV browser: CSS transform/transition only (no container queries, no :has, no view transitions), a one-time "tap to enable sound" gesture to unlock audio autoplay, and a visibilitychange handler that reconnects and resyncs by revision when the TV wakes. Acceptance: feature-verifier PASS doc with screenshots of an idle board, a mid-flip transition, the QR overlay and the audio-unlock prompt; a manual pass on the actual Samsung TV; zero console errors.
  4. Phase 4 — the phone controller. Route /b/:boardId/c exchanges the pairing token for a controller grant, then offers a manual editor: six row inputs, a color picker per segment, a live mini-preview and a Send button, plus a history strip to re-flip a past snapshot. Also owns the board's sound settings — pick a sound pack from the SFX array or mute entirely; the setting rides on the board record so the TV picks it up over the same WebSocket push. Acceptance: feature-verifier PASS on the golden path (scan → pair → type → board flips) and on one error path (expired token → "rescan the QR", no state change); mute from the phone silences the next flip on the display.
  5. Phase 5 — the LLM agent. BoardAgent Effect service on claude-sonnet-5: system prompt that teaches the model the 6×24 constraint and the palette, structured-output call via output_config.format, Effect Schema decode, retry with the decode error fed back, then the Phase 1 repair pass; ANTHROPIC_API_KEY read through the CloudflareEnv tag, never process.env; tagged errors BoardGenerationError and LlmRefusedError mapped in tagToTRPC; tRPC board.generate takes a text prompt plus the current grid as context and is stateless — one shot per call, no conversation history. Acceptance: a 20-prompt eval script yields 20 valid grids; refusal and timeout paths each covered by a unit test with a stubbed client.
  6. Phase 6 — walkie-talkie. Hold-to-talk button on the controller records with MediaRecorder, POSTs the blob to /api/transcribe, Workers AI Whisper returns a transcript, the transcript flows into board.generate and the board flips. Acceptance: feature-verifier PASS driving the flow with a pre-recorded audio fixture; empty transcript shows "didn't catch that" and leaves the board untouched.
Explicitly out of scope for the MVP — but the seams are left in

Automations (a cron that refreshes the board each morning with weather or calendar) are a paid feature, per round 1 — not built now, but nothing in the design blocks them. Two seams make it cheap later: BoardAgent is a plain Effect service that takes a prompt and returns a grid, so a Cloudflare Workflow or a Cron Trigger can call it with no HTTP request in play; and board_snapshot.source is an enum from day one (manual | llm | automation) so automated flips are distinguishable in history without a migration. Gating goes on the existing Better Auth role/plan check — the same adminProcedure pattern the admin dashboard already uses.

Multi-board UI — a board picker and a "new board" flow. The schema and the DO are already per-board, so this is UI-only work, not a data migration.

R2 — not needed. Boards are tiny JSON, and SFX ship as static assets under public/ through the existing ASSETS binding. The missing r2_buckets block in wrangler.jsonc stays a known starter gap for whenever file-upload is actually exercised.

Golden path

Walkie-talkie, end to end — the flow that has to feel like magic.

sequenceDiagram
  participant P as Phone (controller)
  participant W as Worker
  participant AI as Workers AI (whisper)
  participant C as claude-sonnet-5
  participant DO as BoardRoom DO
  participant TV as TV (display)

  TV->>DO: WS subscribe (board 42)
  P->>W: POST /api/transcribe (audio blob)
  W->>AI: transcribe
  AI-->>W: "put up something nice for dinner guests"
  P->>W: board.generate(transcript)
  W->>C: prompt + BoardMessage json_schema
  C-->>W: BoardMessage JSON
  W->>W: Effect Schema decode -> compile -> 6x24 grid
  W->>DO: setGrid(grid, rev+1)
  DO->>DO: persist snapshot to D1
  DO-->>TV: push grid
  DO-->>P: ack + echo grid
  TV->>TV: flap animation + SFX, row by row

One-shot by design (decision from round 1): each press of the button is an independent generation. No conversation history is carried between presses, so there is no per-board chat state to store or evict — a follow-up like "make it funnier" is simply a new prompt that includes the current board as context.

Testing plan

Open questions

  • How does a board get created in the first place — auto-create one on first login, or a "new board" screen in the dashboard? Phase 2 needs some answer, even if it's a seed row.
  • Does a paired phone stay paired indefinitely, or should the grant expire (a day? a week?) and need a rescan?
  • How does the board animate a change — all 144 tiles at once, a left-to-right cascade, or row by row? Real Vestaboards cascade, and it's most of the charm, but it costs animation-timing work in Phase 3.
  • Should the LLM be allowed to see anything about you — time of day, the previous board, who's paired — or is the transcript the whole input?
  • How many sound packs at launch, and where do the audio files come from — recorded, bought, or generated?

Verdict

Answer the six decision cards above, then approve — or annotate anything and request changes.
