flappyboard MVP

2026-07-27 · features: split-flap-board, phone-control, llm-board-agent · draft · round 0

TL;DR

A 6×24 split-flap board renders full-screen on the TV and is driven live from a phone that pairs by scanning a QR code — no login on the phone. State lives in one Durable Object per board and pushes over WebSockets, so a flip on the phone lands on the TV in well under a second. The headline feature is walkie-talkie mode: hold to talk, Whisper transcribes, Claude returns a schema-constrained board message, and an Effect Schema decode plus deterministic repair pass guarantees a renderable 6×24 grid every time — the board never breaks because the model got creative.

The Durable Object is the only writer of live state; D1 is the durable snapshot and history. The Worker never holds board state in memory — it validates, then hands the grid to the DO.

Decisions needed

1. How do the TV and phone stay in sync? The TV is a passive display; the phone is the writer. Both need the same grid within a moment of any change.

OptionProsCons
Single authoritative writer, sub-100ms push, no polling cost, hibernation means an idle board costs nothing; SQLite-backed DOs are on the Workers free plan New binding + a migrations block in wrangler.jsonc; one more runtime concept in the codebase
Zero new bindings, works with the tRPC layer exactly as it exists today Up to 1s of visible lag on every flip, ~86k reads/day per idle board, and manual-edit feedback feels laggy on the phone
One-way push, no DO Doesn't actually work — each request may hit a different isolate, so there's no shared fanout point to broadcast from

2. What shape is the board data the LLM produces? This is the single highest-leverage decision in the plan — it determines how often the model can produce something unrenderable. 6×24 = 144 cells.

OptionProsCons
~10× smaller output, so far fewer tokens and far fewer ways to be wrong; the compiler owns wrapping, centering, charset legality and the 6×24 invariant, so the grid is correct by construction; still gives per-word and per-block color Can't express arbitrary per-cell pixel art
Total control, per-cell color, pixel art possible 144 objects per response; the model must count to 24 six times — the most common structural failure mode, and the expensive one to retry
Covers art/patterns later without giving up the safe default path Two code paths and two validators to test from day one
What "rows of colored segments" looks like 
{ "rows": [
    { "align": "center", "segments": [ { "text": "GOOD MORNING", "color": "yellow" } ] },
    { "align": "center", "segments": [ { "text": "SEAN", "color": "white" } ] },
    { "align": "left",   "segments": [ { "text": "  ", "color": "red" },
                                       { "text": " 3 MEETINGS TODAY", "color": "white" } ] }
  ] }

A segment of pure spaces with a color is how you get solid color tiles — same primitive as a real Vestaboard's color chips. The compiler word-wraps each row to 24, applies alignment, upper-cases, maps unsupported characters, and emits exactly 6 × 24 cells. Rows omitted by the model become blank rows.

3. Which model generates the board? The task is small (a transcript in, a few rows of witty copy out) but it must respect a JSON schema and be fun to read.

OptionProsCons
Schema enforced server-side via output_config.format, so malformed JSON is essentially off the table; best copywriting; $5/$25 per MTok and each call is a few hundred tokens New secret (ANTHROPIC_API_KEY) and an outbound dependency
Same SDK and same structured-output support at $1/$5 per MTok; fastest time-to-flip Noticeably blander board copy — the thing you actually look at all day
Binding already exists, no key, no egress, cheapest Weakest instruction-following of the three — the retry/repair loop would earn its keep more often

Whichever wins, the retry-and-repair loop in decision 4 stays — schema enforcement stops malformed JSON, not a model that writes a 40-character line.

4. What happens when the model's output still doesn't fit? You asked for a validator that retries until valid. The open question is what the last resort is.

OptionProsCons
The board always updates — bounded latency, bounded cost, and a repair pass (clip to 24, drop rows past 6, unknown colour → white) that is pure, synchronous and unit-testable A pathological response can render as clipped text rather than an error
Never shows a degraded board; failures are visible instead of silently absorbed Unbounded retries on a bad prompt, and a walkie-talkie that sometimes just does nothing is the worst possible UX for this product
Fastest and cheapest — one call, always Gives up the model's chance to fix its own mistake, so more clipped boards

In all three options the retry is Effect.retry with Schedule.recurs, the schema is Effect Schema (never Zod), and the failure is a tagged BoardGenerationError mapped in tagToTRPC. The repair pass also gets a fuzz test: a corpus of adversarial model outputs must all produce a valid 6×24 grid.

5. How does the phone earn the right to drive the board? The QR code is on a TV in a room — treat anything on screen as public.

OptionProsCons
No login on the phone (the whole point of scanning); token is HMAC-signed with BETTER_AUTH_SECRET, single-use, ~2 min TTL and rotates on the display; the grant is a scoped cookie the DO recognises, revocable from the TV One more token type to implement and test
Real identity per controller, reuses the shipped auth feature as-is Typing a password on a phone to change the words on your own TV; kills the scan-and-go experience
Simplest thing that could work; fine for a board in your own living room The URL is displayed on a TV — anyone who photographs it controls the board forever, with no way to revoke

6. How does hold-to-talk become text? Walkie-talkie is the headline feature, so this path has to work on the phone you actually own — iOS Safari.

OptionProsCons
Uses the AI binding that's already declared and has no consumers yet; identical behaviour on every browser; the audio blob is a fixture you can replay in tests Round-trip latency after release (upload + transcribe) instead of live text
Free, no upload, live interim transcript while you hold the button Support and quality vary by browser and OS version; nothing to replay in a test, so the feature-verifier can't drive it headlessly
Best latency where supported, correctness everywhere else Two transcription paths in the MVP — more surface than the first version needs

Plan of record

Six phases, three brain features. The scope policy allows one in-progress feature at a time, so they ship in order: split-flap-board (phases 1–3) → phone-control (phase 4) → llm-board-agent (phases 5–6). Every phase ends green on bun run typecheck && bun run test; the user-visible ones also need a feature-verifier PASS doc.

  1. Phase 1 — domain core, no UI and no network. Effect Schema for BoardMessage (rows of colored segments) and BoardGrid (6×24 cells), the charset table, the layout compiler (upper-case, word-wrap to 24, align, map unsupported chars), and the repair pass. Acceptance: unit tests cover compiler and repair; a fuzz corpus of adversarial model outputs all produce a structurally valid 6×24 grid; no Zod anywhere.
  2. Phase 2 — persistence and the realtime room. D1 tables board + board_snapshot with a Drizzle migration and an Effect.Service BoardRepository; the BoardRoom Durable Object with WebSocket hibernation and last-write-wins on a monotonic revision; BOARD binding plus a migrations tag in wrangler.jsonc; tRPC board.get / board.setMessage / board.history. Acceptance: two browser tabs on the same board, a write in one appears in the other in under 300ms; repository unit-tested; bun run build passes (catches Workers-compat breakage).
  3. Phase 3 — the TV display. Route /b/:boardId renders 144 flap tiles at full-bleed with a CSS flip animation and per-cell color, subscribes over WebSocket, and overlays a QR code that encodes the current pairing token. Acceptance: feature-verifier PASS doc with screenshots of an idle board, a mid-flip transition and the QR overlay; zero console errors.
  4. Phase 4 — the phone controller. Route /b/:boardId/c exchanges the pairing token for a controller grant, then offers a manual editor: six row inputs, a color picker per segment, a live mini-preview and a Send button, plus a history strip to re-flip a past snapshot. Acceptance: feature-verifier PASS on the golden path (scan → pair → type → board flips) and on one error path (expired token → "rescan the QR", no state change).
  5. Phase 5 — the LLM agent. BoardAgent Effect service: system prompt that teaches the model the 6×24 constraint and the palette, structured-output call, Effect Schema decode, retry with the decode error fed back, then the Phase 1 repair pass; tagged errors BoardGenerationError and LlmRefusedError mapped in tagToTRPC; tRPC board.generate takes a text prompt. Acceptance: a 20-prompt eval script yields 20 valid grids; refusal and timeout paths each covered by a unit test with a stubbed client.
  6. Phase 6 — walkie-talkie. Hold-to-talk button on the controller records with MediaRecorder, POSTs the blob to /api/transcribe, Workers AI Whisper returns a transcript, the transcript flows into board.generate and the board flips. Acceptance: feature-verifier PASS driving the flow with a pre-recorded audio fixture; empty transcript shows "didn't catch that" and leaves the board untouched.

Error paths

FailureDetected byHandled byUser sees
Model output fails schema decode Effect Schema decode failure in BoardAgent Retry ×2 with the decode error appended, then the deterministic repair pass Board still flips; a small "trimmed to fit" toast on the phone
Model declines the request stop_reason === "refusal" checked before reading content LlmRefusedError → tagToTRPC → BAD_REQUEST "Can't put that on the board" — board unchanged
WebSocket drops on the TV onclose on the client Exponential-backoff reconnect, then a full snapshot fetch to resync by revision Board keeps showing the last grid; a faint "reconnecting" dot in the corner
Pairing token expired or already used HMAC / TTL / single-use check in board.pair PairingTokenInvalidError → UNAUTHORIZED; the display rotates its token "That code expired — rescan the QR on the TV"
Whisper returns an empty transcript Empty/whitespace text from the AI binding TranscriptionFailedError; no LLM call is made "Didn't catch that — hold and try again"; board untouched
Two controllers write at once Stale revision number on the incoming command DO serialises writes; last write wins and the loser gets the new grid echoed back Both phones converge on the same board; the loser's editor refreshes
Durable Object unreachable Failed stub fetch in BoardRoomService Read path falls back to the latest D1 snapshot; write path returns a tagged error TV renders the last known board; phone shows controls disabled

Testing plan

Open questions

  • Does the board ever act on its own — a cron that refreshes it each morning with weather or calendar — or is every change human-triggered in v1?
  • Is one board per account enough for v1, or do you want several (living room, office) from the start?
  • Should the walkie-talkie hold a conversation (multi-turn, "no, make it funnier") or is every press a fresh one-shot board?
  • What is the TV actually running — a browser on a smart TV, an Apple TV, a Raspberry Pi in kiosk mode? It decides how hard we can lean on modern CSS and WebSocket reliability.
  • Flap sound effect on transition — charming or unbearable after a week?
  • The starter marks file-upload shipped but wrangler.jsonc has no R2 binding — fix that separately, or leave it until something needs R2?

Verdict

Answer the six decision cards above, then approve — or annotate anything and request changes.
