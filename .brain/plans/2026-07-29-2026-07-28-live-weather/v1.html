Live weather

2026-07-28 · feature: live-weather (new) · draft · round 0

TL;DR

The board's weather numbers are wrong by 6–10 °C because we ask a search index for a value that changes hourly, and an index returns whatever the crawler last saw. There is no cache to disable and no freshness parameter to set — web_search has no such knob, and web_fetch can only fetch URLs already in the conversation. The fix is to stop searching for weather and call a weather API: Open-Meteo, free, no key. Keep web_search for scores and news, where it already works.

Context

Web search landed in PR #4, squash-merged to main as de1717d, and its own feature doc already states the problem under "Known limitation: search gives sourced figures, not current ones". Against Open-Meteo as ground truth, every configuration tried was materially stale on temperature:

ReadingBoard saidRealError
filtered search (verification run C)22 °C16.0 °C+6.0
filtered search (verification run E)19–22 °C23.3 °C−1.3 to −4.3
filtered search (re-measured)14 °C24.4 °C−10.4
direct search17 °C24.4 °C−7.4

Run C's verification doc also records one segment, FEELS LIKE EVENING 5 °C, that "does not correspond to anything" — invented, because the model had a 6×24 grid to fill and no real fields to fill it with. That is a second bug with the same root cause.

The accuracy pattern is structural, not random, which is what points at the fix:

Asked forResultWhy
Sunsetaccurate to the minuteComputed from date + latitude. Static all day — a stale snippet cannot be wrong about it.
Scores, newsspecific and checkableFacts about the past. They stop changing once published.
Temperature6–10 °C off, every timeThe one value that changes hourly. A crawled snippet is old by construction — sometimes literally tagged "AS OF 7:24 AM".

Three things were checked against the API reference rather than assumed, and they close off the cheaper-looking fixes:

  • web_search's only parameters are max_uses, allowed_domains/blocked_domains and user_location. There is no freshness or cache parameter to turn off.
  • web_fetch only fetches URLs already present in the conversation. It is not a crawler, so it cannot independently go get a live page — which is why adding it alongside search (per the feature doc) changed nothing.
  • Prompt caching (cache_control) caches our prompt prefix. It has no bearing on search results at all.

The important property: on the weather route the model is handed typed values it did not choose and told that fields absent from the payload may not appear on the board. That is what kills the invented FEELS LIKE EVENING 5 °C class of bug — not a sterner prompt.

Decisions needed

1. How does real weather data reach the model?

The board agent currently has no client-side tool-execution loop — callModel handles server tools, pauses and retries, but never executes a tool itself. That makes this a real architectural choice, not a detail.

OptionProsCons
Fits the existing Route shape exactly — routeFor already returns one. No tool loop to build. The model cannot choose a location or skip the call, and we can hard-constrain it to the fields we actually fetched. One deterministic HTTP hop. The router must return more than a boolean (intent + place). Weather becomes a first-class case in the agent rather than one tool among many.
General — the same loop later serves any tool. The model decides when it is needed, so the router stays a boolean. Needs a real tool-execution loop in callModel, which is the largest piece of new machinery here. The model picks the location string, so it can still get that wrong, and it may decline to call the tool at all (exactly what happened with web_fetch).
Zero work. Sunset, scores and news are already good. Temperature stays 6–10 °C wrong, and "don't invent numbers" remains a claim the measurements refute. not recommended

2. How does "Oslo" become a latitude and longitude?

Open-Meteo's forecast endpoint takes coordinates, not place names.

OptionProsCons
Authoritative and free, same provider, no key. Returns a canonical name we can print on the board, so the board says which Springfield it meant. Resolves the ambiguity rather than guessing at it. A second HTTP hop before the forecast (two round trips per weather board). Needs its own not-found path.
Zero extra hops — the router call already happens, so coordinates ride along in the same structured output. Reintroduces the exact failure we are fixing. A model inventing coordinates is a model inventing numbers; a plausible-but-wrong lat/lon returns real, precise, confidently wrong weather for somewhere else.
Fast path for the common cities, correct path for everything else. Two code paths and a reconciliation rule for when they disagree, to save one HTTP call on a request that already costs a model round trip.

3. What goes on the board when the weather lookup fails?

Open-Meteo is down, or the place cannot be geocoded. Note this cuts against the router's existing instinct — routeFor deliberately fails open to searching, on the argument that routing a weather board to the plain path costs the whole feature.

OptionProsCons
Never displays a wrong number. The whole feature exists so the board stops asserting figures it cannot stand behind, and a silent fall back to the stale path is precisely how you end up back where you started. A blank-ish board is a worse living-room experience than a slightly wrong one, and the family cannot tell an outage from a bug.
Always produces a board, and matches the router's existing fail-open posture. Degrades to today's behaviour rather than to nothing. Degrades to today's behaviour — which is the bug. Silently, with no way for anyone looking at the board to know which path produced it.
The person who pressed the button learns immediately, and the board keeps its previous message rather than losing it to an error state. Loses the request entirely. Also means an upstream outage looks to the user like the product is broken.

4. How much of Open-Meteo do we take now?

One forecast call can return current conditions, today's min/max, and sun times together — the marginal cost of more fields is zero HTTP and a few tokens.

OptionProsCons
Fixes exactly the measured defect and nothing else. Temperature, apparent temperature, humidity, wind, condition code — already more than a 6×24 board can show well. Sunset stays search-derived, even though search happens to get it right and the API would give it for free.
Same single call. Retires the last reason a weather board would ever search, and "high 24 / low 15, sunset 21:58" is a genuinely nicer board. More fields than fit, so the model chooses what to show — reopening a little of the judgment we are trying to remove.
Weather becomes the first of several typed sources (transit, air quality, tides) behind one seam. Designing a framework from one example. Weather is the only case with a measured defect. premature

5. When does this get built?

feat-010 tv-pairing is in-progress and 010/011/012 are all code-complete with verification outstanding. The one-in-progress policy is the constraint.

OptionProsCons
Obeys the scope policy without a special case. Three features already owe verification — adding a fourth in flight is how none of them get finished. The board keeps showing wrong temperatures until then.
Small and touches a different area of the code entirely (board-agent.ts, not pairing), so it would not collide. Four features in flight, and the TV work is the one with a hardware deadline nobody else can unblock.
Lets v0.2.0 headline live weather truthfully instead of shipping notes hedged around a 10 °C error. Blocks a release that is otherwise ready, for a fix that can ship as v0.2.1 a few days later.

Plan of record

Double-click a phase to rewrite it; x to drop it.

  1. Phase 1 — the pure core. New app/lib/board/weather.ts: Effect Schema for the Open-Meteo forecast and geocoding responses, a WMO weather-code to words map, unit derivation (C and F from one value rather than trusting two), and a renderer that turns a decoded reading into the compact lines a 6x24 board can hold. Pure and total — no fetch, no Effect service, injectable clock. Acceptance: unit tests cover every WMO code branch, a malformed payload decodes to a typed failure rather than throwing, and the renderer never emits a line over 24 characters.
  2. Phase 2 — the service. New app/services/weather.ts as an Effect Tag + Layer per rules/services.md, with a WeatherUnavailableError tagged error registered in the AppError union, APP_ERROR_TAGS and tagToTRPC (the runtime allowlist that is not type-checked — see recipes/add-tagged-error). Bounded timeout, bounded response size, no retries beyond one. Acceptance: unit tests with a stubbed fetch prove a 500, a timeout, an unparseable body and an empty geocoding result each produce the typed error and never a partial reading.
  3. Phase 3 — the router learns intent. BOARD_ROUTER_SCHEMA grows from one boolean to an intent plus an optional place string, and routeFor returns the new WEATHER route when the intent is weather and a place is present. The existing fail-open-to-searching behaviour is preserved for every other outcome, including an unparseable router response. Acceptance: table-driven tests over router outputs assert the route chosen for weather-with-place, weather-without-place, other-live-data, self-contained, and each malformed shape.
  4. Phase 4 — wire the weather route. On the WEATHER route: geocode, fetch, decode, then call Sonnet with a weather-specific system prompt that supplies the real fields and forbids any figure not present in them, with tools omitted entirely the way PLAIN_ROUTE already omits them. Failure follows decision 3. Acceptance: with a stubbed weather service the generated grid contains only supplied values, and an injected extra-field prompt cannot produce a number that was not in the payload.
  5. Phase 5 — prove it against ground truth. A browser walk driving the real phone controller against the real API, with the board's numbers checked against an independent Open-Meteo call made at the same moment — the same method the run-C and run-E verification docs used to catch the staleness in the first place. Acceptance: a verification doc per brain playbook verify, with the measured delta stated as a number. The bar this feature exists to clear: temperature within rounding of ground truth, not within 6 degrees.
  6. Phase 6 — correct the record. Update the llm-board-agent feature doc's "search gives sourced figures, not current ones" section to say what now happens instead, and note in rules/services.md that Open-Meteo is an unauthenticated external dependency in the request path. Acceptance: harness-check 7/7 and no stale claim left asserting the board searches for weather.

Testing plan

Open questions

  • Open-Meteo's free tier is rate-limited per day. The spend cap already bounds us to 20 generations per board per hour, so we are nowhere near it — but is an unauthenticated third-party dependency in the request path acceptable at all, or should this be behind a key on a paid tier before it is load-bearing for a wall-mounted board?
  • Should the board ever show the reading's observation time? It is honest and it is what would have exposed the stale-snippet problem immediately, but it costs a row on a 6x24 grid.
  • Does a household want a default location, so "what's the weather" with no place works? That is a per-board setting and a schema change, and it is the sort of thing that turns a fix into a feature — probably its own plan.
