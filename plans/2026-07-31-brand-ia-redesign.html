flappyboard — brand, IA & UX redesign

2026-07-31 · features: brand-system, app-ia, console-journey-v2, front-door · reviewed · round 1 — approved

Round 1 outcome — approved, with a bigger cut than proposed

"Approved, but one thing to note with the design is keep in mind the phone is our controller so let's make it easy to interface."

The standing constraint that follows: every phone surface is judged on thumb reach and target size before it is judged on looks — primary actions in the bottom third, ≥44×44 everywhere, nothing load-bearing in a top corner, no hover-only affordance. This outranks visual preference in any conflict.

The board-count branch is deleted entirely

Two annotations did it: "I don't even want a new board setup — we should just scan the QR code or input the code and it adds rather than creating a board and linking it" and "I don't think we even check the boards — we should just link a new one if not already existing. And then once we're there that's when we can have the settings."

A board is a TV. resolveAutoLink, the picker, the <select>, the receipt and /link's entire manual mode are deleted. defaultBoardName survives — it auto-names the new board. There is never a question to answer.

The controller becomes the app

Per "maybe we should have 2 tabs, 1 for the board settings and 1 for the content" — the separate board-detail page is folded into the controller. One surface, two tabs, at the already-frozen /b/:boardId/c: Content (live grid as the primary instrument, row wells behind a toggle, hold-to-talk, history) and Settings (TV address, devices + count, rename, un-pair, delete).

The path stays frozen deliberately: the TV encodes /b/:boardId/c?t=… into the QR it re-mints from its own loader, so a path change only reaches a TV that reloads.

The one thing this cut opens up

If scanning always creates a board, sprawl is possible — a TV whose cookie is evicted shows a fresh code, the owner scans, and a second board appears for the same television. There is no stable TV identity across cookie loss to dedupe on. Proposed handling, consistent with "don't check the boards": the happy path never asks, and a single secondary line — "…or attach this TV to an existing board" — covers the case where the owner spots the mistake. A one-tap escape, not a branch. Open for phase 3; do not build the picker back in through the side door.

TL;DR

The MVP works but the app around the board is stock shadcn boilerplate, and the paths through it are longer than they need to be. This extracts the researched hardware design language already living inside the board into the real token contract, ships two self-hosted typefaces, and cuts the route map down — new user reaches a working board in 3 stops instead of 5. The board render itself is frozen; it is the reference, not the subject.

Product brief

Problem + evidence

Someone buys into a product that mimics a ~$3k living-room object, and the software around it introduces itself as a developer boilerplate.

  • app/routes/home.tsx — the front door — still returns title: "Cloudflare SaaS Starter", six cards advertising the stack, and a section printing /start-task, /verify-done and .brain/recipes/ paths to end users.
  • app/locales/en/dashboard.json:5 says it out loud, in shipped copy: "This is the post-auth landing page of the boilerplate. Below is a tour of what's wired and where to look in the code."
  • All four "explore" cards on that page pass disabled={!isAdmin} (dashboard/_index.tsx:129,139,150,161), so a household user's signed-in home page is four greyed-out cards.
  • app/app.css is stock shadcn "neutral", unmodified — verified against the file. Meanwhile flap-tile.tsx, board-frame.tsx and console.tsx carry a researched physical palette measured off a real Vestaboard with PIL (.brain/features/split-flap-board/runs/2026-07-27-progress.md), entirely in hardcoded hex, unreachable by any other surface.
  • Two source files apologize in their own comments for the same gap. console.tsx: "Condensed uppercase for labels. No condensed face ships with the app, so the register is reached with uppercase + wide tracking." flap-tile.tsx: Inter reads as a "geometric web font rather than the tighter industrial cut."

Three defects surfaced while researching this, none of them part of the ask:

  • Non-admin users cannot sign out. authClient.signOut() appears in exactly one file — admin/layout/nav-user.tsx:49. Every household user is stuck signed in.
  • The /:lng routes are a soft-404 farm. i18nServer uses remix-i18next's default detection order (searchParams, cookie, session, header) — there is no pathname detector, and no route reads params.lng. And index("routes/home.tsx") under prefix(":lng", …) makes /:lng a catch-all, so /pricing, /about and /asdf all return 200 with the marketing page instead of 404.
  • The focus ring paints and is invisible. The recorded defect note (.brain/runs/2026-07-30-focus-ring-defect.md) has the wrong mechanism — --tw-ring-shadow does reach box-shadow, verified in the compiled CSS. The real cause: --ring: oklch(0.708 0 0) at 50% alpha composites to ≈1.9:1 on white; the WCAG 2.2 floor is 3:1.

User + job to be done

A person standing in their living room holding a phone, with a TV in front of them, who wants the board to say something. They have just bought in. Their job in the first five minutes is to get words onto the screen across the room; their job for the next year is to change those words in under ten seconds without thinking about it. They are not evaluating a stack. They will never open /admin.

The second user is a family member whose phone has just scanned a QR code on the TV — no account, no login, one job: type something funny and send it before the moment passes.

Non-goals

  • Redesigning the board render. A reader would reasonably expect a "premium redesign" to touch the product's centerpiece. It is explicitly frozen: it is already the best-researched surface in the repo, and its rAF hot loop, its glyph metrics and its documented Samsung Tizen constraints (flap-tile.tsx:11-17) are the highest-risk code to disturb for the least gain.
  • Redesigning /admin. Operator surface, not customer surface. It keeps its sidebar and its inherited kitchen-sink.tsx — which is also the ready-made regression surface for the token pass, since it renders every shadcn primitive on one page.
  • Changing the pairing protocol. No change to the device-code handshake, the grant/device epochs, the HMAC token prefixes, or the JavaScript-disabled submit contract. This is a re-skin and a step-count cut, not a re-plumb.

Product decisions

1. Where does a returning owner land when they open the app?

Today: /dashboard, which links to /boards, which links to the controller. Three stops to change a message.

OptionProsCons
Zero taps before typing for the overwhelming majority (one board, one TV). Mirrors the resolveAutoLink precedent exactly — pure, testable. A single-board owner who wanted to manage has to tap the brand mark to reach the rack.
One predictable destination. Nothing to explain. Keeps a permanent interstitial between the owner and the only thing they came to do.

2. After approving a TV, does the phone show a confirmation page?

Today it lands on /link?paired=…, a page whose only job is to offer a link to the controller.

OptionProsCons
One stop and one tap fewer. Refresh-safety gets better — it moves onto the controller's already-idempotent loader and a bespoke branch deletes. Also fixes a latent wart: the manual action currently returns on success, so a refresh re-POSTs a spent code. The TV flipping is the only confirmation. Invalidates three assertions in an existing verification doc.
Explicit "it worked" moment on the device the user is looking at. A stop with no decision on it. Buys no-JS users nothing — the controller's editor is entirely mutation-driven and dead without JS either way.

3. When a family member's phone pairs, do we stop them to ask its name?

OptionProsCons
A guest reaches the board in two taps. The owner's revoke UI already buckets rows by last-seen, so unnamed devices are still identifiable. Fewer devices end up named, making a long device list harder to read.
Names get captured at the one moment the user knows whose phone it is. A modal between a guest and the thing they scanned a code to reach.

4. Does the landing page's board move?

OptionProsCons
Shows the mechanism — the entire reason to buy — without becoming a carousel. Cheap, and reduced-motion falls back to the settled state for free via the existing snapTo. A visitor who scrolls past in the first second misses it.
More chances to catch the eye; can demo range. Reads as an ad. A board in a real home changes a few times a day, not every four seconds — it would misrepresent the product's own cadence.
Zero risk, zero cost. Shows a picture of a board instead of a board.

Technical decisions needed

5. How is the hardware palette expressed in the token contract?

OptionProsCons
Every surface gets the brand; the always-dark hardware ladder gets its own scope without deleting light mode. First real use of the documented escape hatch. ~45 shadcn files keep working untouched because the names don't change. Two places to reason about. Requires declaring both [data-surface] and .dark [data-surface] so the scope can't lose on specificity.
One place. Maximum coherence. The ladder is always dark. This either deletes light mode or invents a "light mode for painted metal", which is a lie about the object.
Zero risk to existing surfaces. Leaves 100% of the app on stock shadcn — re-creates the exact drift this plan exists to fix.

6. What is the global corner radius?

Currently 0.625rem (10px) — the shadcn default. console.tsx documents the object as "0px on panels and buttons, 2px on wells and flaps". This is the single most visible token in the app.

OptionProsCons
Highest-leverage single change. Instantly reads as hardware rather than SaaS. --radius-sm: calc(var(--radius) - 4px) goes negative, which is invalid, so the declaration is silently dropped and .rounded-sm stops applying across avatar, badge, checkbox, dropdown-menu, select. Needs a max(0px, …) guard.
Still tightens noticeably; the negative-calc trap disappears at sm. Reads as "a slightly tighter web app", not as an object.
Zero regression surface. Keeps the single loudest tell that this is a shadcn default.

7. Which two typefaces ship?

Both must be self-hosted and OFL-licensed. Constraint: a 2017 Samsung Tizen panel is Chromium 56, so anything on the TV path must be a static cut — variable fonts need Chromium 62+.

OptionProsCons
Archivo's roots are American gothic news/wood type — the register of a split-flap unit — and it has a real wdth axis, so the condensed look console.tsx fakes with tracking becomes a genuine cut. Plex Mono is engineering-instrument, not IDE: slashed zero, unambiguous 1/l. Two new families to subset and self-host. Neither covers CJK.
Saira is more overtly industrial/technical; also a real wdth axis. Reads more "sci-fi dashboard" than "household object". JetBrains Mono is unmistakably a code editor face.
Smallest change; no display-face risk. Leaves the app at one-and-a-bit faces and leaves both source files' own complaints unanswered.

8. /admin is scoped as untouched — but it is a one-way door.

app-sidebar.tsx:49-65 has no link back to the product. The only exits are the browser's back button or typing a URL.

OptionProsCons
One line. Fixes a real dead end without touching admin's design. Breaks the "byte-frozen" promise on /admin.
Scope stays exactly where it was set. The dead end stays.

9. app/components/file-upload.tsx has zero consumers — grep returns only the file itself. So /api/upload-file has no UI caller at all.

OptionProsCons
Removes dead UI; leaves the R2 wiring (feat-003) intact for a future use. An endpoint with no caller is still surface area.
Smallest attack surface; feat-003 is recorded as shipped-but-broken anyway (R2 was never provisioned). Retiring a shipped feature is a bigger call than a redesign should make silently.
Nothing to argue about. Dead code stays dead code.

Plan of record

Four PRs, sequential. Tier boundaries: thin stops after phase 1, complete after phase 3, gold after phase 4.

  1. Phase 1 — Brand foundation (brand-system). Retune app.css (global contract, radius + max(0px,…) guard, --signal, --text-*, --flap-*, --font-*, kill the hardcoded bg-white dark:bg-gray-950); add [data-surface="hardware"] and apply it on the four console routes; ship both typefaces self-hosted and remove the Google Fonts link; fix the focus ring app-wide and delete the two hardcoded workarounds; pin --font-flap to Inter behind a shared FLAP_GLYPH_CLASS; re-point console.tsx at var(--hw-*) with no API change; rewrite design-system.md. Acceptance: golden board screenshots still match; design:audit stops emitting fontFamilies < 2; keyboard walk shows a visible ring on every route; /admin/kitchen-sink renders every primitive without a dropped radius.
    Why all of this in one phase?

    Every later phase is built from shadcn primitives whose radius, ring and surface colors come from here, and the font change moves every text metric in the app. Landing any piece later means re-measuring everything shipped in between. The one that is easy to underestimate: if [data-surface] does not exist yet, phase 3 writes style={{ color: CONSOLE.ink }} again and phase 1's work gets unpicked.

  2. Phase 2 — IA & navigation (app-ia). Delete /dashboard and the six /:lng aliases; split /boards into a rack and a /boards/:boardId detail; build boards/_layout.tsx + app-header.tsx + user-menu.tsx; add sign-out for non-admins; add pure resolveSignedInHome(boardCount); add redirect shims so no existing URL 404s. Acceptance: every old URL redirects rather than 404ing; a non-admin can sign out; /pricing returns 404 instead of the marketing page; both board actions still carry their own requireSession.
  3. Phase 3 — Pairing & composer (console-journey-v2). Pairing code becomes six live flap tiles on /tv; collapse the /link receipt and replace the <select> with one button per board row; demote the device-name prompt into the nameplate; promote the composer's live grid to the primary instrument with the row wells behind a toggle. Acceptance: the measured step counts in the success metric are hit; the no-JS submit contract still passes with JavaScript disabled; resolveAutoLink's signature and return values are unchanged.
    The risk in this phase

    message-editor.tsx is 1265 lines — the largest file in the redesign. It gets a structural read before any edit, and the pass splits into its own PR if the diff stops being reviewable.

  4. Phase 4 — Front door (front-door). Rebuild home.tsx around a live board that spells its own headline, with the missing instruction ("on your TV's browser, go to yourhost/tv") on the page; rewrite home.json in both locales; merge login and sign-up into one toggled page defaulting to sign-up when next carries a pairing code. Acceptance: no string in the shipped landing page mentions the boilerplate, the stack, or a brain command; a zh visitor sees no Latin-face fallback mismatch.

Testing plan

Blast radius, measured: 52 test files, almost all pure logic and untouched by CSS.
